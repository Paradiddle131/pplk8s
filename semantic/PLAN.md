# Semantic layer and metrics agent — plan

The second track of this repository, separate from the Airflow lab ([`../PLAN.md`](../PLAN.md), sealed for this topic).
It shares the warehouse, the dbt project and the Compose stand-ins; it changes a DAG only to give a domain it adds a full lineage (SL-8, the lab's D38).
Progress lives in the issues under the maps: [Map #99](../../../issues/99) (R1-R7, done) and [Map #135](../../../issues/135) (the use case, U1-U6, labels `semantic` and `use-case`), then, in the owner's order of 2026-10-31, [Map #199](../../../issues/199) (more domains), [Map #197](../../../issues/197) (the questions business users ask), [Map #200](../../../issues/200) (one governed semantic layer for every agent), [Map #212](../../../issues/212) (the semantic track on a free-tier GCP project, SL-13) and, low priority, [Map #198](../../../issues/198) (the eval); this file holds what binds the work: the goal, the requirements, the decisions and the exit.
Decisions are a register: one row per live decision, amended in place, a superseded row deleted in the PR that supersedes it; git is the history.

## 1. Goal

Prove that an open-source dbt project can carry a semantic layer that an LLM agent queries instead of writing SQL, on the lab warehouse, and that the same YAML feeds the warehouse catalog and the authored context a native BigQuery data agent takes at work.
The audience is a team whose data already lands in BigQuery, whose agents guess which table to trust, and who will not run dbt Cloud.
The track builds and deploys one agent, the semantic agent (SL-2); the text-to-SQL baseline beside it in the code is the eval's control, run in-process to measure the semantic layer's value, and is never deployed (SL-5).

The use case widens it: show, end to end and on a BigQuery engine, a warehouse such a team's agents read correctly, from raw to business-ready, with the documentation, monitoring, access and migration around it (U1-U6).

## 2. Requirements

- R1 Every calculated field lives in exactly one metric definition.
- R2 Metrics are queryable locally (`mf` CLI and Python API), with no dbt Cloud.
- R3 An agent-facing catalog is generated from the dbt manifests and persisted as warehouse comments.
- R4 The agent answers through metric tools only; an eval set scores it against a text-to-SQL baseline with the same model, an eval arm rather than a second agent.
- R5 The freshness of each metric, from `ops.readiness`, reaches the answer.
- R6 Agents read gold, exposed and metrics only, marked in dbt.
- R7 Dialect-neutral SQL, a compile-only `dbt-bigquery` target, and a written mapping to BigQuery descriptions, Knowledge Catalog and the native data agent's context.

The use case (Map #135):

- U1 Layers and metric home: raw → clean → business-ready models over several domains; each calculated field defined once as a metric.
- U2 Agent-readable documentation: descriptions, naming, a glossary, and their mapping to BigQuery descriptions and Knowledge Catalog, as a standard with a check.
- U3 Monitoring: an alert when a source stops flowing; discrepancy checks between layers.
- U4 Access and audit: which agent reads which data; every agent query logged.
- U5 Migration: new layers built beside the old, consumers switched one at a time on a parity report.
- U6 BigQuery executed, not only compiled.

Out of scope: GCP spend beyond the Always Free tier, and Airflow on GCP (SL-13); paid models, Gemini Enterprise, dbt Cloud, dbt Fusion, a custom chat UI, writes or approvals.

The agent never reads `information_schema`. **A question answered the same way every time is a dbt saved query** (`models/semantic/saved_queries.yml`, its question in `config.meta.question`): the generator compiles it into a verified query beside the per-metric ones and lists it in the agent catalog, and the lab agent runs one by name through `query_metrics`' `saved_query`, narrowed by dates and filters, so its three data tools stay three (#164). | The native agent's inputs are exactly what the manifests hold, so its context is a build artefact; BigQuery, Knowledge Catalog and the agent get the same words. A term never repeats a metric, because the metric is already its own glossary entry (R1). A saved query is versioned with the metrics and validated by the parse and `mf validate-configs`, which is what a verified query is at work; it fixes its metrics and group-bys, so free-form questions keep going through the metrics. |
| SL-4 | **Agents read gold, exposed and metrics only**, marked `access: public` (group `analytics`) in dbt; silver and bronze stay `protected` and out of the catalog. The semantic models sit on silver, so an agent reaches silver only through a metric's definition: MetricFlow for the lab agent, the authored context's aggregations, glossary and verified queries for a native data agent. **Every answer carries the freshness of its metrics:** the catalog names each metric's readiness products, `<pipeline>.<layer>` of the models it reads (`sales.silver`); the agent's `after_tool_callback` attaches to every answered data call the newest `ready` interval end of the products of the metrics the result names (or the call asked for) from `ops.readiness`, late by the lab's D37 rule against `ops.product_deadlines` (a layer without a deadline of its own takes its pipeline's), and one statement the answer quotes word for word; a late product is said so, and a result that names no metrics says that its freshness is unknown and why. `agent_metrics` reads those two `ops` tables and no other. **The rules agents rely on are one standard, [`docs/agent-ready-warehouse.md`](../docs/agent-ready-warehouse.md)** (a dataset and model prefix per layer, the relation named without the prefix, snake case, which models are public, semantic models on silver, what each description says), **and `dbt/scripts/check_standard.py` enforces it offline on every parse in `make dbt-validate` and the dbt image build. Every public model enforces a dbt model contract with a `data_type` on every column**, spelled so Postgres and BigQuery both accept it. | Trust is marked in dbt, not in a prompt. One check over the manifests generalises the metric and catalog checks, and runs where `dbt parse` does; `dbt-project-evaluator` was rejected because it builds its rules in the warehouse, assumes staging, intermediate and marts names, and has no rule for metrics or semantic models. A contract makes a renamed, dropped or retyped column an agent relies on a failing build, not a stale catalog; it is dbt-native, so it reaches BigQuery unchanged, and views get its name and type check without constraints. Model versions wait until a consumer needs two shapes at once. Freshness is a tool result the model quotes, checked by a test, never prompt logic; it is attached around the toolset, not inside it, so it survives the swap to `DataAgentToolset` (#177). The product is the layer the metric reads, because that is the row the DAGs write for it (`returns` has no pipeline-level row); the pipeline's deadline covers its layers, since the pipeline is not ready before they are. |
| SL-5 | **The semantic agent's value is measured by a scored eval against a text-to-SQL control; the control is an eval arm, not a second agent.** About fifty business questions across the domains and question shapes (totals, subsets, ratios, changes over a period, running totals, filters on dates and amounts, weekdays and top N, cohorts), and conversations whose turns share a session (a follow-up that adds a breakdown, changes the period or switches the metric, "how was that computed?", a term with more than one meaning), with expected numbers computed from the warehouse go through the semantic agent and through a baseline with one `execute_sql` tool over the same gold and exposed tables (the "ADK schema-driven" pattern), same model, both scores side by side. The baseline runs only in-process in the eval (and beside the agent in the local `adk web` demo); the image and the Deployment serve the semantic agent alone (#163). ADK's own eval engine (`LocalEvalService`) runs it, scored by six custom metrics in `evals/eval_config.json`, each on the turns it applies to: `answer_correct` (the answer carries the warehouse's number, or declines where no metric covers the question), `metric_choice` (the semantic agent queried the expected metrics), `freshness_quoted` (its answer quotes the freshness its queries returned), `definition_quoted` (asked how a figure was computed, the answer quotes the metric's description) and `term_disambiguated` (asked with a term an `Ambiguous on its own:` glossary term defines, the answer asks which meaning or gives each meaning's number; one number and no question fails) and `planted_ignored` (asked about rows whose text holds an instruction the fixture plants in a campaign's or a customer's name, the answer neither repeats it nor obeys it: none of its strings in the answer, no `query_metrics` call naming the metric it asks for; the report says whether a tool result showed it to the model); `make agent-eval` writes `docs/research/semantic-agent-eval.md`. ADK's built-in `tool_trajectory_avg_score` compares every tool argument, which free-form group-bys and filters never match exactly, and its LLM-judged metrics would double the free-tier spend; the custom metrics check what matters, the number, the metric, the definition and the question back, with code rather than a judge model. A term with more than one meaning is a glossary term whose description says so, not a prompt rule, so the native data agent, whose glossary holds only a term's words, reads the same sentence (#183). |

| SL-9 | **Every hand-off between layers reconciles in `dbt build`, as dbt tests named `hop_<from>_to_<to>`, on Postgres and the emulator alike.** Bronze → silver: silver holds exactly bronze's latest load of each key, rows and amounts (the generic `latest_load_reconciles`, re-deriving the latest load by joins on maxima rather than silver's `row_number`); silver → gold and gold → exposed: singular tests per model, counts and sums per key; metric → gold: the generic `matches_metric` on a hand-written column renders its simple metric from dbt's graph (aggregation, expression, filters on its own semantic model's dimensions, day of its `agg_time_dimension`), or a cumulative metric as its simple input over the window of days ending on each of the column's days, or a conversion rate as MetricFlow 0.15 computes it (base and conversion rows joined on the entity within the window of days, each conversion row counted once on the latest base day it joined, divided by the base metric per base day; within a tolerance of 1e-6), and compares it per day; the conversion rates' columns are `gold.customer_engagement_daily`'s funnel rates and `gold.lead_conversion_daily`'s lead-to-booking rate, one row per day, since a rate cannot be summed over `gold.marketing_daily`'s channels. | SL-10 | **Every data query an agent runs leaves one row in `ops.agent_queries`, written by ADK's `after_tool_callback` on both agents as `agent_audit`, a role that may only insert into that table; a data query is a call to any tool but the ones the toolset seam names as reading only the catalog (#177), so a renamed or added data tool is audited and a forgotten catalog tool is over-audited, never skipped;** the row holds the agent, user, session, invocation and call, the metrics, filters and arguments or the SQL, the rows returned, the freshness statement and the error. BigQuery IAM cannot express insert-only: inserting needs `bigquery.tables.updateData`, which also allows UPDATE and DELETE, so on the lab project `agent-audit` holds the narrowest predefined role, Data Editor, on `ops.agent_queries` alone, and may also read, change and delete that one table's rows; the agent's own account reads `ops.readiness` and `ops.product_deadlines` by table grants, each granted once dbt has created the table (`platform/gcp/access.yaml`, #209). Rejected for #177: a list of audited tool names (the swap to `DataAgentToolset` renames the data tool, so it would go unaudited), a flag on each tool (the toolset ADK builds carries none), and freshness as a tool of its own (the model may skip a call; a callback cannot be skipped). The agents' roles stay without a single write grant because the read-only transaction is not the only guard to rely on: the baseline's SQL could leave it (`commit; begin read write`, measured before the tool held a call to one statement), so INSERT on the audit for `agent_sql` would let a model forge or flood it; a separate writer is how BigQuery works too, where the platform, not the caller, writes the audit log. Failing closed keeps "every query logged" true. A macro rather than models: dbt creates no roles, and a model would rebuild the audit table it must keep, or need an incremental model that never refreshes and a column type (`text[]`) Postgres and BigQuery spell differently; `run-operation` is dbt's own entry point for such administration, and the Compose init no longer holds a second copy. Rejected: INSERT for the agents' own roles (forgeable, as above), an ADK plugin (`adk api_server` builds the runner, so a plugin needs an `App` wrapper for one callback), auditing in the session store (the session holds the tool call, but a session can be deleted and is not queryable as a log). |

## 5. How this track works

- Issues hold progress and the PR body is the record of a change (what, evidence, decisions, open); this file changes when a decision, a requirement or a step changes.
- A research doc is evidence with an expiry: it stays while code does not yet hold what it says, and the PR that absorbs it deletes it (S1 and S2 absorbed the spike's YAML, pins and context schema into `dbt/` and the generator; S3 to S5 absorbed the rest, the native patterns and the unverified points into [`docs/semantic-layer-on-bigquery.md`](../docs/semantic-layer-on-bigquery.md), and S5 deleted the spike doc).
- Lessons for the work platform (the native data agent, BigQuery descriptions, Knowledge Catalog) go in § 6, one line each with evidence.
- Risks: `dbt-metricflow` pins `dbt-core` to a minor range, so the two move together and the parity check re-runs after either moves; the model is a free tier, so every live run is opt-in.
- The Python API is the `mf` CLI's own surface, not a reinvention: `mf query` builds the same `MetricFlowQueryRequest.create(...)` and calls `MetricFlowEngine.query` or `.explain`, which the agent and the catalog generator call too. dbt documents only the CLI, so that surface is undocumented and held by the pin; `services/semantic-agent/tests/test_metricflow_surface.py` checks it offline in `make agent-test` (the symbols, `create`'s keywords, the result fields read, the licence), so a bump fails there naming it rather than in the pod (#165).

## 6. Lessons for work

- Define each business metric once in the semantic YAML and generate descriptions, glossary and the data agent's context from the manifests; hand-written context drifts from the models (S0: one derived metric reproduced a hand-written finance table to the cent).
- A data agent's verified queries and glossary can be build artefacts: MetricFlow lists a metric's dimensions and compiles its SQL with no warehouse connection, so one offline step turns the semantic YAML into the authored context (S2: eight metrics, eight compiled queries that run on the warehouse).
- A text-to-SQL agent over curated gold tables answers a subset the gold grain dropped (orders by status, returns by reason) with a confident wrong number instead of declining; metrics over the detail tables with filterable dimensions answer it (S3 eval, same free model: semantic agent 15 of 15, baseline 13 of 15, both misses wrong numbers).
- Scope each agent's data access with a read-only warehouse role, not its prompt: the baseline's role refused `silver`, `ops` and every write whatever SQL the model wrote (S3); at work that is a dataset-level IAM grant per agent identity.
- Put freshness in the tool result, not the prompt, and attach it around the toolset (ADK's `after_tool_callback`) rather than inside it, so a swap to `DataAgentToolset` keeps it (#177): the callback reads the readiness ledger and its deadlines for the products a metric reads and returns one sentence the model quotes; a free model quoted it word for word in every answer (S4: 13 of 13, ten of them "Late: ...").
- Give an ADK agent its retry options in its own request config: ADK's eval engine adds 7 attempts to a request without them, and its LiteLLM wrapper turns those into `num_retries`, so a refused key was sent 8 times per question whatever the model was built with (#116).
- A dbt project can prove its BigQuery path with no GCP account: a `bigquery` output with a placeholder `oauth-secrets` token compiles offline with `--no-introspect`, and MetricFlow then writes the data agent's verified queries in BigQuery's dialect (S5: 16 models and 8 verified queries, parsed as BigQuery SQL).
- A dbt project's BigQuery path can run, not only compile, with no GCP account: dbt-bigquery's `api_endpoint` reaches the goccy BigQuery emulator, which builds and tests the models and serves MetricFlow, once a shim answers `routines.list` and reports DDL jobs as scripts (#125: 66 of 66 nodes, eight metrics equal to gold and exposed).
- A ratio such as cost per conversion belongs in the semantic layer, not in a dashboard table: a daily table of ratios invites the average of the daily values, which is not the period's ratio (#126 fixture: cost per booking 130.00 over two days, 152.50 as the average of the daily values); a MetricFlow ratio metric divides the totals for whatever period and grouping is asked.
- Migrate semantic YAML with dbt's own tool, then prove the numbers, not just the parse: `dbt-autofix` 0.22.6 moved all 16 metrics to the latest spec and `mf validate-configs` passed, but dbt-core 1.12.6 silently drops `fill_nulls_with` there, so seven counts and sums turned NULL instead of 0 in groups without rows; only the parity check against the hand-written tables caught it (#137).
- Reconcile every layer hop inside the build, not in a script beside it: 26 dbt tests named after their hop (bronze → silver latest load, silver → gold, gold → exposed, metric → gold) run wherever `dbt build` runs, the emulator included, and each seeded fault failed exactly the hop it broke; a simple metric can be rendered from dbt's graph in a test, so its parity with the hand-written table fails the build rather than an on-demand check (#131).
- On dbt-core 1.12.6's latest YAML spec, declare a metric over other metrics (ratio, derived, conversion) in a top-level `metrics:` file, not on a model: one on a model is added twice by the next partial parse after any edit of that model's YAML (`dbt found two metrics with the name ...`), which only `--no-partial-parse` clears (#149).
- Keep a source's freshness thresholds in dbt and let the warehouse carry the verdict to monitoring: `dbt source freshness` runs the project's `on-run-end` hook (on by default in dbt 1.12.6, `source_freshness_run_project_hooks`), so one macro writes each table's status into a table the monitoring exporter reads, and the alert never holds a second copy of the thresholds (#130: a stopped, a late and a dropped table recorded `error`, `warn` and `runtime error`, one row each).
- Audit an agent's queries with an identity the agent cannot use: a text-to-SQL tool's SQL can leave a read-only transaction (`commit; begin read write`), so only privileges keep an audit table unforged; at work the Data Access audit log, which BigQuery cannot turn off, is that record, and job labels carry the session it served (#132).
- Hold a text-to-SQL tool to one statement in the driver, not by parsing the SQL: on the simple query protocol `commit; set statement_timeout = 0; select pg_sleep(11)` lifted the baseline's 10 s timeout and `commit; begin read write` left its read-only transaction, while the extended protocol (psycopg `prepare=True`) refuses a second statement before any runs (#153); BigQuery runs a semicolon-separated query as a multi-statement script, so an `execute_sql` tool there needs the same refusal.
- Give a data agent each categorical dimension's values, not only its name: told only that `return__reason` exists, a free model filtered on "damaged goods" for `damaged` and answered a confident €0 (#157); declaring the codes with dbt's `accepted_values` puts them in the generated catalog, and the tool refuses any other value with the list, so the model retries with the right one.
- Declare a code column's values over the rows already loaded, not only the next ones: the new `accepted_values` test on `slv_returns.reason` failed a lab warehouse whose bronze held codes from before it (`late`, check markers), which a fresh fixture never shows (#157). Conform the old codes in silver, bronze kept raw, so the test holds over all history and a new partner code still fails the build; a `where` cutover or `severity: warn` would keep the build green but leave values a group-by shows and the agent's filter refuses.
- Rehearse a migration with the consumers in dbt: one exposure per dashboard, agent and automation naming the table it reads, a parity model comparing each old table with its new model in the consumer's column names, and a test that fails the build switching a consumer with an unaccepted difference or out of order (#133: on the fixture, a legacy revenue that counted cancelled orders differed on 4 of 12 country-days and held the agent back; the dashboard switched, every field equal).
- Serve an agent's tools over MCP with the audit and freshness in a function both surfaces call, not in the agent framework's callback: an MCP client calling the tools skips ADK's `after_tool_callback`, so the lab moved them into `guard.guarded`, and the MCP server names its caller from the bearer token, never from an argument a model could set; ADK 2.13's `McpToolset` works against MCP SDK 2.3 (where `FastMCP` is renamed `MCPServer`), and a free model answered an eval question through it with its audit row written as the client's agent.
- Never hand a model's text to MetricFlow's `where` unchecked, even as a quoted literal: MetricFlow renders the whole filter with Jinja before it compiles SQL, so the value `'{{ 7*7 }}'` filtered on `'49'` (#161); the sandbox stops code from running, but the filter means something other than what was asked and answers with a confident number. Refuse `{{`, `{%` and `{#` in a value; dbt-mcp's `query_metrics`, which takes a `where` template string, carries the same gap.
- Keep an agent's warehouse objects (its roles, grants and audit table) in the dbt project as a `run-operation` macro dispatched per adapter, not in the lab's init scripts: on an empty database `make agent-warehouse`, the fixture and one turn gave the answer, its audit row and "Freshness unknown" with no Airflow and no ledger, and the same macro created the audit table on the BigQuery emulator (#166). A role is not a model, and a model would rebuild an audit table it must keep.
- Test a conversion metric's numbers, not only its validation: MetricFlow 0.15 accepts a filter on the conversion side (on the input or on the simple metric) and then drops it or fails to resolve it, so a view-to-cart rate counted the page view itself and read 1.0 on every day; count the step with a `case` expression instead, and remember that a `window` of N days at day grain means fewer than N days after the base (2 days is the same day or the next) (#188).
- Test SQL that calls BigQuery's AI functions against a golden set, never against the emulator alone: the goccy emulator 0.8.1 answers `AI.CLASSIFY` with the first category whatever the input and `AI.SCORE` with 0.5, while `AI.GENERATE` and remote models fail to parse, so a build there passes with wrong labels ([`docs/text-signals.md`](../docs/text-signals.md), #191).
- Give a label prompt's golden set its own calls, labelled by the same macro into its own incremental model, rather than golden labels on production rows: the agreement test then holds on every build whatever days landed, and a new prompt version is scored on the same calls; on the fixture's 15 golden calls a free model reached kappa 0.76 to 1.00 per signal against thresholds written before the first comparison (#241).
- Guard `GREATEST` and `LEAST` with an explicit `CASE` when an argument can be NULL in a model that runs on both Postgres and BigQuery: Postgres ignores NULL arguments (measured: a label share with no baseline got the band [0, 1], caught by a dbt unit test), while BigQuery returns NULL if any argument is NULL ([mathematical functions](https://cloud.google.com/bigquery/docs/reference/standard-sql/mathematical_functions#greatest), stated), so the same SQL answers differently on the two (#248).
- Pin down what a query's dates do to a metric filter before a definition relies on it: MetricFlow 0.213 computes `{{ Metric('orders_total', group_by=['customer']) }} >= 2` over all time whatever the query's dates, so a customer with one order on the day asked and others before counts as a repeat customer (2 October's repeat revenue 868.65, not the 467.90 a date-limited count gives); a definition that needs a windowed count says so in its own metric.
- Write a period-over-period metric's arithmetic for the warehouse it will run on, and test it on weeks of data: a derived metric's `expr` is passed through as SQL, so `(bookings - bookings_prior_week) / bookings_prior_week` divided integers on Postgres and gave 0 for every week (BigQuery's `/` always returns FLOAT64), and `coalesce(revenue_eur, 0)` on the current week gave the week after the last data a growth of -100 %; `* 1.0` and no coalesce fixed both, and a comparison with SQL written by hand over six weeks of fixture now holds them (#181).
- Ship a SQL-only dbt project to BigQuery without what the adapter needs only for Python models: dbt-bigquery 1.12.1 requires Vertex AI's client, pandas and pyarrow (for Python models, BigFrames and DataFrame reads), and they were 121 of the image's 270 MiB as a registry stores it; a lock compiled with `uv pip compile --excludes` and installed with `--no-deps` brought it to 149 MiB, and the image's own `dbt build` with its tests and MetricFlow's queries passed on the emulator without them (#206). Vertex AI is imported only when a Python model runs; Dataproc's client is imported at load, so it stays.
- Run the SQL on real BigQuery before trusting an emulator's green: BigQuery refuses a parameterized type in CAST (`cast(amount as numeric(12, 2))`: "Parameterized types are not allowed in CAST expressions"), yet creates the view that holds one and fails only when it is queried; the goccy emulator and sqlglot accept it, so six bronze models passed every emulator build and failed 17 nodes on the lab project's first run (#275). Cast to the bare type, and check compiled SQL for parameterized casts; and don't round there to mimic the scale: the emulator's ROUND on NUMERIC goes through FLOAT64 and broke a gold -> exposed hop.
- Say in the glossary when a word means more than one metric, and let the agent ask: with `Customers` and `Sales` described as ambiguous, a free model gave each meaning's number, named, on both ambiguous questions and then followed the user's choice, while the text-to-SQL baseline, with no glossary, answered "customers in September" with one of three readings (10 active customers, not 9 signups or 30 to date) and no word that others exist (#183 eval: conversations 7 of 7 against 4 of 7).
