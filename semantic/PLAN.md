# Semantic layer and metrics agent — plan

The second track of this repository, separate from the Airflow lab ([`../PLAN.md`](../PLAN.md), sealed for this topic).
It shares the warehouse, the dbt project and the Compose stand-ins; nothing in it changes a DAG.
Progress lives in the issues under [Map #99](../../../issues/99); this file holds what binds the work: the goal, the requirements, the decisions and the exit.
Decisions are a register: one row per live decision, amended in place, a superseded row deleted in the PR that supersedes it; git is the history.

## 1. Goal

Prove that an open-source dbt project can carry a semantic layer that an LLM agent queries instead of writing SQL, on the lab warehouse, and that the same YAML feeds the warehouse catalog and the authored context a native BigQuery data agent takes at work.
The audience is a team whose data already lands in BigQuery, whose agents guess which table to trust, and who will not run dbt Cloud.

## 2. Requirements

- R1 Every calculated field lives in exactly one metric definition.
- R2 Metrics are queryable locally (`mf` CLI and Python API), with no dbt Cloud.
- R3 An agent-facing catalog is generated from the dbt manifests and persisted as warehouse comments.
- R4 The agent answers through metric tools only; an eval set scores it against a text-to-SQL baseline with the same model.
- R5 The freshness of each metric, from `ops.readiness`, reaches the answer.
- R6 Agents read gold, exposed and metrics only, marked in dbt.
- R7 Dialect-neutral SQL, a compile-only `dbt-bigquery` target, and a written mapping to BigQuery descriptions, Knowledge Catalog and the native data agent's context.

Out of scope: real GCP spend, IAM, Gemini Enterprise, dbt Cloud, dbt Fusion, a custom chat UI, writes or approvals.

## 3. Decisions

| # | Decision | Why |
|---|---|---|
| SL-1 | **The semantic layer is dbt's: MetricFlow semantic models and metrics in the dbt project, over silver and gold, every calculated field defined once as a metric.** `dbt-metricflow[dbt-postgres]` 0.15.0 (MetricFlow 0.213.0) on the project's `dbt-core` 1.12.5 pin, a daily time spine model, `mf validate-configs` as a stage check, the `mf` CLI or Python API as the only query path; no dbt Cloud. | The spec is open source and runs on Postgres and BigQuery alike (S0 spike: eight metrics validate; `net_revenue_eur` matches `exposed.net_sales_daily` to the cent; S5: the project parses and compiles on BigQuery's adapter unchanged). The hand-written gold and exposed aggregates stay as the parity oracle. Rejected: Cube and the Boring Semantic Layer (a second model beside dbt), LookML (needs Looker), dbt Cloud (not what the client runs). |
| SL-2 | **The agent is an ADK agent and a Cloud Run stand-in** (`services/semantic-agent/`, namespace `workloads`): ADK owns the runner, the sessions (`DatabaseSessionService` on a database of the Compose metadata-db Postgres), serving (`adk api_server`; `adk web` is the demo surface) and evaluation (`adk eval`); the model sits behind a `MODEL_BACKEND` seam (OpenRouter free tier here, Gemini at work). **Its only data tools are `list_metrics`, `describe_metric` and `query_metrics`**, the stand-in for `DataAgentToolset.ask_data_agent` on a native BigQuery data agent. `query_metrics` takes metric names, group-bys, structured filters (`{dimension, operator, values}` on categorical dimensions) and a date range, each checked against the catalog, and builds MetricFlow's filter itself; it never takes SQL. The warehouse enforces each agent's reach with a read-only role: `agent_metrics` (silver and semantic, for MetricFlow) and `agent_sql` (gold and exposed, for the baseline). | Mirrors the work target's "ADK governed" pattern with the data agent swapped for the semantic layer: the agent code moves, only the toolset changes. Nothing custom for state, sessions or the event loop (owner, 2026-10-29). Airflow never calls the agent. Deployed (#111), the Deployment's initContainer runs `dbt parse` and the catalog generator for the database the pod reads, because MetricFlow's compiled SQL names that database; the image only carries the project. |
| SL-3 | **The semantic YAML is the single source of agent context.** One generator (`dbt/scripts/build_catalog.py`, `make dbt-catalog`) reads `manifest.json` and `semantic_manifest.json`, asks MetricFlow offline for each metric's dimensions and compiled SQL, and writes the agent catalog the toolset reads (`target/catalog/agent.json`) and the native data agent's authored context (`system_instruction.yaml` in Google's documented form: tables, fields and aggregations from the measures, relationships from entities, glossary from metric descriptions; and `example_queries.json` from each metric's compiled SQL). The warehouse comments are dbt's own: `persist_docs` on gold and exposed, and a `semantic.metrics` model rendered from dbt's graph at build time. The agent never reads `information_schema`. | The native agent's inputs are exactly what the manifests hold, so its context is a build artefact; BigQuery, Knowledge Catalog and the agent get the same words. Building the warehouse half in dbt means it lands wherever dbt builds, BigQuery included, with no loader beside it and no copy that can lag the YAML. |
| SL-4 | **Agents read gold, exposed and metrics only**, marked `access: public` (group `analytics`) in dbt; silver and bronze stay `protected` and out of the catalog. The semantic models sit on silver, so an agent reaches silver only through a metric's definition: MetricFlow for the lab agent, the authored context's aggregations, glossary and verified queries for a native data agent. **Every answer carries the freshness of its metrics:** the catalog names each metric's readiness products, `<pipeline>.<layer>` of the models it reads (`sales.silver`); `query_metrics` returns their newest `ready` interval end from `ops.readiness`, late by the lab's D37 rule against `ops.product_deadlines` (a layer without a deadline of its own takes its pipeline's), and one statement the answer quotes word for word; a late product is said so. `agent_metrics` reads those two `ops` tables and no other. | Trust is marked in dbt, not in a prompt. Freshness is a tool result the model quotes, checked by a test, never prompt logic. The product is the layer the metric reads, because that is the row the DAGs write for it (`returns` has no pipeline-level row); the pipeline's deadline covers its layers, since the pipeline is not ready before they are. |
| SL-5 | **Proof is a scored eval, not a demo:** about fifteen business questions with expected numbers computed from the warehouse, through the semantic agent and through a baseline agent with one `execute_sql` tool over the same gold and exposed tables (the "ADK schema-driven" pattern), same model, both scores side by side. ADK's own eval engine (`LocalEvalService`) runs it, scored by three custom metrics in `evals/eval_config.json`: `answer_correct` (the answer carries the warehouse's number, or declines where no metric covers the question), `metric_choice` (the semantic agent queried the expected metrics) and `freshness_quoted` (its answer quotes the freshness its queries returned); `make agent-eval` writes `docs/research/semantic-agent-eval.md`. Live runs are opt-in and budgeted against the free tier; a spent quota skips with its reason, never silently: a model call that fails after its retries ends the turn with an answer naming the failure (ADK's `on_model_error_callback`), the eval waits out a per-minute limit once (at most 90 s), and a spent daily quota or a refused key (401, 403) skips the questions left, keeps the last report and exits 3, as does a run where no question got an answer; `make agent-eval` checks the key on OpenRouter's `/key` endpoint before it builds. Unit tests never reach a live model. | Shows the semantic layer's value, not the model's; the baseline is what most teams run today. ADK's built-in `tool_trajectory_avg_score` compares every tool argument, which free-form group-bys and filters never match exactly, and its LLM-judged metrics would double the free-tier spend; the two custom metrics check what matters, the number and the metric. |
| SL-6 | **One project, two dialects: each construct Postgres and BigQuery spell differently is a dbt `adapter.dispatch` macro (`dbt/macros/dialect.sql`), and `profiles.yml` carries a compile-only `bigquery` output.** It builds its client offline from a placeholder `oauth-secrets` token, and `dbt compile --no-introspect --no-populate-cache` never queries. `make bigquery-check` parses, validates and compiles the semantic path on it, parses every compiled model as BigQuery SQL (sqlglot), and runs the catalog generator, whose verified queries come out in BigQuery's dialect. The tlc models stay Postgres-only, marked `-- dialect:`. | R7 asks for dialect-neutral SQL; dispatch is dbt's own mechanism, and the Postgres SQL stays as it was apart from type-name case. `dbt.date_spine` counts its days with a warehouse query, so the spine is a two-line macro instead. A real BigQuery run is out of scope (no GCP spend); sqlglot is the strongest offline check of the dialect, and the doc names what only a real run can show. |

## 5. How this track works

- Issues hold progress and the PR body is the record of a change (what, evidence, decisions, open); this file changes when a decision, a requirement or a step changes.
- A research doc is evidence with an expiry: it stays while code does not yet hold what it says, and the PR that absorbs it deletes it (S1 and S2 absorbed the spike's YAML, pins and context schema into `dbt/` and the generator; S3 to S5 absorbed the rest, the native patterns and the unverified points into [`docs/semantic-layer-on-bigquery.md`](../docs/semantic-layer-on-bigquery.md), and S5 deleted the spike doc).
- Lessons for the work platform (the native data agent, BigQuery descriptions, Knowledge Catalog) go in § 6, one line each with evidence.
- Risks: `dbt-metricflow` pins `dbt-core` to a minor range, so the two move together and the parity check re-runs after either moves; the model is a free tier, so every live run is opt-in.

## 6. Lessons for work

- Define each business metric once in the semantic YAML and generate descriptions, glossary and the data agent's context from the manifests; hand-written context drifts from the models (S0: one derived metric reproduced a hand-written finance table to the cent).
- A data agent's verified queries and glossary can be build artefacts: MetricFlow lists a metric's dimensions and compiles its SQL with no warehouse connection, so one offline step turns the semantic YAML into the authored context (S2: eight metrics, eight compiled queries that run on the warehouse).
- A text-to-SQL agent over curated gold tables answers a subset the gold grain dropped (orders by status, returns by reason) with a confident wrong number instead of declining; metrics over the detail tables with filterable dimensions answer it (S3 eval, same free model: semantic agent 15 of 15, baseline 13 of 15, both misses wrong numbers).
- Scope each agent's data access with a read-only warehouse role, not its prompt: the baseline's role refused `silver`, `ops` and every write whatever SQL the model wrote (S3); at work that is a dataset-level IAM grant per agent identity.
- Put freshness in the toolset's result, not the prompt: the tool reads the readiness ledger and its deadlines for the products a metric reads and returns one sentence the model quotes; a free model quoted it word for word in every answer (S4: 13 of 13, ten of them "Late: ...").
- Give an ADK agent its retry options in its own request config: ADK's eval engine adds 7 attempts to a request without them, and its LiteLLM wrapper turns those into `num_retries`, so a refused key was sent 8 times per question whatever the model was built with (#116).
- A dbt project can prove its BigQuery path with no GCP account: a `bigquery` output with a placeholder `oauth-secrets` token compiles offline with `--no-introspect`, and MetricFlow then writes the data agent's verified queries in BigQuery's dialect (S5: 16 models and 8 verified queries, parsed as BigQuery SQL).
