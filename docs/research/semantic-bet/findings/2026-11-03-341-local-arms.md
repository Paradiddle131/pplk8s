# The local arms on the frozen set, under the rule (#341)

Question (Q8, a slice of #333): on the frozen set ([`semantic_bet.yaml`](../../../../services/semantic-agent/evals/semantic_bet.yaml), 96 cases), how do the two arms that need no GCP, `custom-metricflow` and `baseline`, score under [`RULE.md`](../RULE.md), and can the run survive the free tier's daily quota?

## What was built

- [`services/semantic-agent/src/semantic_agent/bet_eval.py`](../../../../services/semantic-agent/src/semantic_agent/bet_eval.py): the bet mode of the eval driver.
  - It asks every (run, case, arm) in that order, each run of a case in a fresh session through the eval's own `evaluate` (ADK's `LocalEvalService`), so a cut pass still leaves both arms paired on the cases it reached.
  - It scores each turn with `bet_rule`: a number turn by `number_right` (a decline is never right), a `define` turn by the eval's definition check, an `ambiguous` turn by `asks_or_gives_each`; a turn that repeats or obeys a planted instruction is wrong.
  - It appends every finished run to [`eval-local.jsonl`](../eval-local.jsonl) (arm, model, run, case, each turn's answer and outcome, the model responses it took); a later pass never asks a logged run again.
  - A run that errors (not a spent quota) is asked again on a later pass, and counts wrong after two errors.
  - It stops on a spent quota or refused key, a time budget (`--minutes`) or a request budget (`--requests`), and rewrites [`eval-local.md`](../eval-local.md) from the log alone (`--report-only` without asking).
- `tests/e2e/agent-eval.sh`: `ARM=bet` (with `RUNS`, `MINUTES`, `REQUESTS`) builds the fixture and runs it, so `make agent-eval ARM=bet` is the entry point.
- `evaluation.py`: a case's outcome now keeps its invocations, its model responses and whether its failure ends the run; nothing it scores changed.
- `tests/test_bet_eval.py`: 10 tests with a scripted model, one of them two runs on two arms where the first pass is cut by a scripted daily-quota error after three answers and the second resumes from the log, asking only the five runs it lacks (`measured`, `make agent-test` 2026-11-03).

## Two reading choices the rule left open

- A `define` turn that fails to quote its definition, or an `ambiguous` turn that silently picks one meaning's number, is **wrong**, not confident-wrong: the rule's confident-wrong needs "a number outside tolerance", and neither turn has an expected number that a stated one misses.
  An `ambiguous` turn whose number matches no meaning is scored as a number turn (confident-wrong unless hedged).
- A planted instruction repeated or obeyed makes the turn wrong even when its number is right: the planted group is reported, never deciding, and a hijacked answer is not a right one.

## What was run

- 2026-11-03T03:42Z–04:03Z, `ARM=bet RUNS=3 MINUTES=30 tests/e2e/agent-eval.sh` on the default free model `nvidia/nemotron-3.5-super-vl:free` (OpenRouter), the fixture rebuilt in `dbt_dev` first; stopped by hand at 400 model responses (the `--requests` budget was added during this run for later passes), to leave most of the shared 1,000 a day to other runs.
- Logged: 95 runs, all of run 1, both arms on cases 1–47 of 96 (baseline 48, `custom-metricflow` 47); 400 model responses (baseline 221, `custom-metricflow` 179), no errors (`measured`, [`eval-local.jsonl`](../eval-local.jsonl)).

| On the 47 cases both arms reached, run 1 | `baseline` | `custom-metricflow` |
|---|---|---|
| Accuracy | 68.1% | 95.7% |
| Confident-wrong, as the code calls it | 19.1% (9) | 0.0% |
| `covered` (45) | 68.9% | 100.0% |
| `trap` (8) | 50.0% | 100.0% |
| `uncovered` (2) | 50.0% | 0.0% |

- Paired, `custom-metricflow` minus `baseline`: accuracy +0.277 [+0.128, +0.426], confident-wrong −0.191 [−0.298, −0.085], both excluding zero (`measured`, [`eval-local.md`](../eval-local.md)).
- `custom-metricflow`'s two misses are honest declines: the temperature in Amsterdam, and the median order value, whose metric it says exists only on the BigQuery warehouse.
- Read by hand, three of the baseline's nine confident-wrong calls are not confident: `orders_over_100` only declines ("cannot be determined"), and its "100" and "1–2" are the question's own numbers echoed; `damaged_returns` and `net_revenue_germany` give another figure beside a sentence saying the asked one is not in the tables ("do not separately identify", "does not provide").
  The other six state a wrong number plainly (e.g. `return_rate_september`: "0% of the 120 orders placed in September 2026 were returned").
  So the code's parser over-counts the baseline's confident-wrong rate on this run (about 6 of 47, 13%, by hand); the log keeps every answer, so a corrected parser rescores it without asking again ([#343](../../../../../issues/343)).

## What it means for the verdict

- On the cases a metric covers, the semantic layer's tools answered right where text-to-SQL over the same warehouse's documented tables often did not: every `trap` (definitions the schema cannot show) right against half, on one run of one free model.
- This is the order the set runs in, not a sample of it: the first 47 cases are mostly `questions.yaml`'s covered ones and only 2 of the set's 29 `uncovered` cases were reached, where the rule expects the semantic layer to lose accuracy by declining; the partial numbers flatter `custom-metricflow`, and only the full set decides.
- Both local arms sit on rungs 3–4, so this pair is descriptive until the managed best is scored (RULE.md § The rule); what it already says is that the custom arm's bar for #333 is high on covered questions.

## Still unknown

- All three runs of both arms: the whole set is about 1,700 model responses, more than the shared 1,000 a day, so [#342](../../../../../issues/342) finishes it one budgeted pass per wake.
- The baseline had no `legacy` schema in reach (`tests/e2e/agent-fixture.sh` builds none), so the `distractor` group measures nothing for it yet; RULE.md wants it in reach for every SQL arm, and that configuration is #333's.
- Unclear turns wait for the blind judge (#333): counted as wrong until judged.
- The request count is the model's responses in the session (`model_responses`): retries inside the model wrapper are not in it; LiteLLM's own `completion()` lines in the run's output matched it within the case in flight.
