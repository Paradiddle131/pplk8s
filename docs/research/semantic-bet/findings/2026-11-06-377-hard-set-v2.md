## The relabelling of v1's 19 uncovered cases

The written rule (#377): a case is `composable` when arithmetic over at most three metric query results gives the number (a grouped query is one result); `uncovered` when it needs row-level SQL no metric composition gives.
Read against the agent catalog (`dbt/target/catalog/agent.json`, built by the fixture run below), after the drafting:

- `composable` (14): `hard_cart_abandonment` (1 minus `cart_to_checkout_rate`), `hard_refund_rate_by_value` (`returns_eur` by `return__order_date` over `revenue_eur`), `hard_budget_pacing` (`ad_spend_eur` over itself plus `remaining_budget_eur`), `hard_ad_spend_wow`, `hard_revenue_per_buyer_country` (`revenue_eur` over `customers_distinct` by country), `hard_cost_per_booking_rise`, `hard_average_order_rise`, `hard_revenue_per_session` (over `site_sessions`), `hard_august_signups_bought` (`customers_distinct` over `signups`, both by signup date), `hard_candidates_still_in_running` (`candidates_in_stage` by stage), `hard_roas_september`, `hard_social_vs_search_lead_gap`, `hard_leads_per_100_social`, `hard_weekend_vs_weekday` (one query by day, averaged by weekday).
- `uncovered` (5): `hard_gmv_september` (no metric sums cancelled orders), `hard_repeat_rate_october` (orders per customer inside the window), `hard_replies_within_12_hours` (time between events), `hard_best_customer_september` (no customer dimension), `hard_first_time_vs_returning` (each order's first-ness).
- So 14 of v1's 19 "uncovered" cases were arithmetic over metrics, as the epic suspected ("about 13").

What each naive query does, in short: takes returns on their return date, not their order's (`hv2_net_revenue_on_september_orders`), or the reverse, only the week's own orders' returns (`hv2_net_revenue_week_returns_credited`); forgets the "as of" date in an anti-join (`hv2_signups_never_ordered`); averages over days that have rows (`hv2_calls_per_day_september`, `hv2_avg_daily_revenue_fiscal_quarter`, `hv2_country_lowest_daily_revenue`); counts each order on its UTC day (`hv2_september_revenue_amsterdam_days`); takes a mean for a median (`hv2_median_gap_between_orders`, `hv2_median_customer_spend`); averages daily rates (`hv2_cancellation_rate_by_value_august`); subtracts return amounts instead of the returned orders' revenue (`hv2_revenue_share_unreturned_orders`); ranks with cancelled orders in (`hv2_top_three_customers_share`); averages every order of the week, not each customer's first (`hv2_first_order_value_october`); turns the anti-join into a join that fans out (`hv2_spend_on_days_without_email_booking`); sums a month's balance snapshots (`hv2_search_budget_left_drop`).

### Why 15 new cases, not about 20

- 90 of the 105 drafts were dropped, for these reasons, the first two the most common (not counted one by one): the fixture cannot answer it or answers it trivially (a handful of rows, 0% or 100%, a constant ratio such as clicks over impressions, which the fixture derives from spend); it repeats a case of the frozen set or v1 on other dates (cost per booking or lead, budget left, median order, session length, days to return, objection rate by topic, ROAS, revenue per buyer); its answer is a small whole number an answer carries by chance; it is ambiguous (a percentile whose method changes the number, the weeks with the most calls tied five ways); or it is the same calculation as a kept case.
- Only one kept case is `covered`: the dashboard figures the drafter wrote were, almost all, ones the two earlier sets already ask; the plan's "about 8 covered but SQL-hard" did not survive the no-repeat rule on this fixture.
  So v2's new cases test SQL past the metrics far more than SQL a metric hides; a v3 that wants the latter needs a richer fixture, not looser rules.
- The criteria are read on the new cases at k = 3: 8 new `uncovered` cases (criteria 2 and 3), 15 new cases (criterion 4); on 8 cases one run moves a share by 4 points, so criteria 2 and 3 are coarse, and #380 reports each with its count and interval.
