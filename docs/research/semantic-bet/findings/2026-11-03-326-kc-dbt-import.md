## What was observed (`measured`, the runs above)

The job and what it created:

```text
job bet-326-trimmed SUCCEEDED 2026-11-03T06:43:43 2026-11-03T07:30:25 {"createdEntries": "97", "createdEntryLinks": "127"}
entries 98 {'entrygroup': 1, 'dbt-metric': 57, 'dbt-model': 16, 'dbt-saved-query': 7, 'dbt-semantic-model': 16, 'dbt-project': 1}
staging: dbt_metadata.jsonl 294,887 bytes each under staging/trimmed-check/ and staging/trimmed/; the 98 entries read back with view=ALL: 290,315 bytes of JSON
```

- The job took 47 minutes from create to `SUCCEEDED` for 97 entries; the `--validate-only` run leaves its jsonl in the bucket but no job resource in `metadataJobs`.
- Every node the trimmed manifest holds came through: 57 metrics of all five types (33 simple, 10 ratio, 6 cumulative, 4 derived, 4 conversion), 16 semantic models, 7 saved queries, 16 models, the project.

What one entry holds (`metric_pplk8s_net_revenue_eur`, aspects `dbt-metric` and `dbt-node`):

```text
fullyQualifiedName: dbt:metric:pplk8s-lab-001.pplk8s.net_revenue_eur
entrySource.displayName: Net revenue (EUR); description: Revenue minus partner returns (finance's net sales).
dbt-metric: {"label": "Net revenue (EUR)", "metricType": "derived",
  "typeParams": "{\"measure\": null, ... \"expr\": \"coalesce(revenue_eur, 0) - coalesce(returns_eur, 0)\", ... \"metrics\": [{\"name\": \"revenue_eur\", ...}, {\"name\": \"returns_eur\", ...}], ...}",
  "baseFilter": "", "timeGranularity": "", "baseMeasures": [], "metadata": ""}
```

- `typeParams` is dbt's `type_params` serialised as one JSON string, not structured fields: a simple metric's aggregation (`metric_aggregation_params`: semantic model, `agg`, `agg_time_dimension`) and a ratio's numerator and denominator are inside that string.
  Our project uses dbt 1.12's metric-level aggregations (0 measures in the manifest), so `baseMeasures` is empty on every metric.
- A metric's filter is kept verbatim as `baseFilter` (`'{{ Dimension(''order__status'') }} <> ''cancelled'''` on `customers_distinct`); a saved query keeps `queryMetrics`, `groupBy` (`Dimension('return__reason')`) and its `meta` (`{"question": "How many partner returns ..."}`).
- A semantic model's `schema` aspect lists its entities (`semantic: METADATA`, `annotations.entityType` primary or foreign, the expression) and its dimensions (`semantic: DIMENSION`, time granularity, the default time dimension): 41 dimensions and 32 entity fields over the 16, matching the manifest's 41 dimensions; foreign entities become `foreignKeys` to the other semantic model.
  Every `dataType` is `UNKNOWN` (no `catalog.json` was staged, as the docs warn), except where our YAML gives `data_type` (`amount: numeric`).
- A model entry keeps its `rawCode` (the Jinja SQL), materialisation, contract flag, columns and descriptions; meta keys come through as labels (`glossary`, `dialects: ["bigquery"]`).

The links (127 in all, every one `reference`):

```text
metric return_rate -> metric returns_on_order_date, metric orders_total
metric revenue_eur (and 6 more) -> semantic_model orders -> model slv_orders -> @bigquery .../datasets/silver/tables/orders
each of the 16 models -> its BigQuery table in silver (campaigns, partners, ..., orders); model slv_returns -> model slv_orders
```

- The chain metric → semantic model → dbt model → BigQuery table resolves for all 16 models in the `US` location; no `schema-join` link was created (the scope allowed it).

Search (`searchEntries`, project-wide, top five):

- A question in plain words finds nothing by keyword and the right metric first with `semanticSearch: true`; the dbt metrics rank beside the `bet_shaped` routines, the `bet_graph` nodes and the legacy tables the other arms created, so an agent's search sees every arm's assets at once.

`lookup_context` (MCP, location `us`):

- One metric (`return_rate`): 3,919 characters of YAML: its description, label, type, `typeParams` as the JSON string, and as related resources its two input metrics with their own `typeParams` and `baseFilter`.
- The metric plus the semantic model `orders`: 15,999 characters: the semantic model's description and fields, the 7 metrics that reference it, and the dbt model `slv_orders` with its columns, labels (the glossary) and the whole `rawCode`.
  The BigQuery table itself is not in the context (two hops away); the table name an agent would query is only in our description text (`Alias silver.orders.`) and the `config(alias='orders')` inside `rawCode`.

  The 98 entries read back as 290,315 bytes of JSON, under the free 1 MiB; the full manifest (2.8 MB, 11 times the trimmed one) would likely pass it, by under a cent a month (about 2 MiB over, at $2 per GiB-month).

## What it means for the verdict

- **The import is complete as a catalogue**: every metric, its type, expression, inputs, filter, label and description is stored and readable, linked down to the BigQuery table; semantic search maps a plain question to the right metric first in all three tries.
- **It is not yet a semantic layer an agent can query**: what an agent gets from `lookup_context` is a definition to read (with the aggregation inside a JSON string and the table two hops away), and it still has to write the SQL itself; whether a data agent turns that into the right number is #327's measurement.
- **Google is building the missing piece**: the catalog's MCP server already advertises `compile_query` / `execute_query` over "a Knowledge Catalog semantic model", with Looker filter expressions, and today it fails on everything; if it ships and accepts dbt-imported semantic models, the gap this bet is about closes on Google's side.
  This is the single fact most likely to change the verdict, and the watch (#335) should track it.
- The import is cheap and repeatable: 249 KiB of manifest gave 295 KB of jsonl and 97 entries in 47 minutes, with the cost check unchanged at $0.000010.

## Still unknown
