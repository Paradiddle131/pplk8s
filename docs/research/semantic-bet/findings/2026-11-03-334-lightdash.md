# Lightdash, open source and self-hosted, on the lab's dbt project (#334, part 2 of 2)

Question (Q9, Lightdash half): what does self-hosted Lightdash give a team on our project for free, and what is Enterprise only?
The dbt-mcp half is [its own finding](2026-11-03-334-dbt-mcp.md).

## What was run

- 2026-11-03T01:45Z, offline: [`probes/334_lightdash.sh`](../probes/334_lightdash.sh): `dbt parse` (dbt Core 1.12.6, the `dev` Postgres target) on a copy of `dbt/`, then `lightdash compile --skip-dbt-compile --no-warehouse-credentials --verbose` with `@lightdash/cli@3.128.0` (Node 24 from npm's `node@24`).
- 2026-11-03T01:50Z, offline, the Compose warehouse up (empty): [`probes/334_lightdash_server.sh`](../probes/334_lightdash_server.sh): `lightdash/lightdash:3.128.0` (released 2026-11-02, 3.2 GB compressed, 15.1 GB unpacked) with pgvector Postgres and MinIO, no `LIGHTDASH_LICENSE_KEY`, `AI_COPILOT_ENABLED=true`, `MCP_ENABLED=true` and a placeholder OpenRouter key; a first user and org through the API, a personal access token, `lightdash deploy --create`, then the MCP endpoint, the AI-agent API, the `slv_orders` explore and `compileQuery`.
  The script's run from a clean Docker state printed the same results as the hand-run steps before it.
- No model was called and nothing left the machine but package and image pulls.

## What was observed (`measured`, the runs above)

- The `dev` target's manifest holds 56 metrics (the approximate median is BigQuery-only, `dbt/models/semantic/semantic.yml`): 32 simple, 10 ratio, 6 cumulative, 4 derived, 4 conversion.
- `Translated 36 MetricFlow metric(s) into Lightdash metrics (skipped 20 unsupported ...)`, straight from `manifest.json`, with no dbt platform and no warehouse:

  | Type | Translated | Skipped, with the CLI's reason |
  |---|---|---|
  | simple | 30 of 32 | `repeat_customers`, `revenue_repeat_customers_eur`: "filter uses template functions other than Dimension()" |
  | ratio | 6 of 10 | `cost_per_lead_eur`, `cost_per_booking_eur`, `return_rate`: "cross-model ratio metrics are not supported"; `repeat_revenue_share`: its input was skipped |
  | derived | 0 of 4 | `net_revenue_eur`: "cross-model derived metrics are not supported"; the three `*_wow_growth`: "offset_window/offset_to_grain, which is not supported" |
  | cumulative | 0 of 6 | "metric type "cumulative" is not supported yet" |
  | conversion | 0 of 4 | "metric type "conversion" is not supported yet" |

- Every skip is named in the CLI's log; none is silent (unlike dbt 1.12's OSI export, which drops the median without a warning).
- 68 explores compiled, 65 clean; the 3 legacy models (`lgc_*`) fail with `No dimensions available` because they document no columns and the probe reads no warehouse catalog.
- The translation keeps the definitions: `slv_orders` gets `revenue_eur` as `SUM(CASE WHEN status <> 'cancelled' THEN amount END)`, `cancellation_rate` as `orders_cancelled * 1.0 / NULLIF(orders_total, 0)`, and `average_order_value_eur` with a generated `average_order_value_eur_denominator`; the descriptions come across.
- The free query API compiles a metric query to one SQL statement (`POST /api/v1/projects/<p>/explores/slv_orders/compileQuery`, revenue and average order value by status): the filters and the ratio inlined, `FROM "warehouse"."silver"."orders"`, `GROUP BY 1`.
- Without a licence, with both features switched on by env vars:
  - `POST /api/v1/mcp` → `422 {"error":"MCP service not available"}`.
  - `GET /api/v1/projects/<p>/aiAgents` → `422 MissingConfigError: Unable to initialize service 'aiAgentService' - no factory or provider.`
  - `/api/v1/health` → `"license": {"hasLicenseKey": false, "valid": false}`.
- Running it needs more than its docs' quick start says: the server exits at boot with `S3-compatible storage is required` until `S3_ENDPOINT`, `S3_BUCKET` and `S3_REGION` are set.

## As documented (`stated`, read 2026-11-03)

- [MetricFlow in Lightdash](https://docs.lightdash.com/integrations/dbt/metricflow): on dbt Core "the CLI reads your project's compiled `manifest.json`"; "No dbt Cloud subscription or dbt Semantic Layer API needed"; dbt Core 1.6 or later; on dbt Cloud it reads the Discovery API with a "Metadata Only" token.
- [AI agents, self-hosted](https://docs.lightdash.com/self-host/enterprise-features/ai-agents): Enterprise; needs `LIGHTDASH_LICENSE_KEY`, then `AI_COPILOT_ENABLED=true` and one provider (OpenAI, Anthropic, OpenRouter, Gemini, Vertex AI, Azure AI, Bedrock).
- [MCP, self-hosted](https://docs.lightdash.com/self-host/enterprise-features/mcp): Enterprise; `MCP_ENABLED=true` "Requires `LIGHTDASH_LICENSE_KEY`"; served at `/api/v1/mcp` over HTTPS.
- [Agent identity](https://docs.lightdash.com/agents/agent-identity): "By default, an agent query uses the same credentials as the person who asked"; a shared agent account per connection is the alternative, and Lightdash "never falls back to the person's own credentials" when one is required; the feature is Beta, Enterprise, behind the `agent-identity` flag.

## What it means for the verdict

- Free Lightdash is a real, offline MetricFlow compiler for the metrics that live on one model: 36 of our 56, definitions intact, behind a metric-level query API an agent could call with an ordinary token.
  That is closer to `custom-metricflow` than free dbt-mcp gets (which has no metric tool at all), but only for single-model simple and ratio metrics.
- What it drops is the hard part of our layer, and the same part the OSI export loses: cumulative, conversion, offset (period-over-period), cross-model ratios and derived metrics, and filters that use more than `Dimension()`.
  An agent over Lightdash's explores would have to rebuild those 20 in SQL, which is where the bet expects agents to fail confidently (#333 can score it).
- The agent and MCP surfaces, and answering as the asking user, are Enterprise: a team gets the semantic model and a query API for free, not the agent.
- For the verdict: borrow, don't adopt.
  Lightdash's translation table (which MetricFlow shapes map to a per-model metric, and which don't) is a ready-made map of what any "compile MetricFlow into something else" path loses, for Knowledge Catalog's import (#326) as much as for Lightdash; a gap-filling repo should not rebuild this compiler.
