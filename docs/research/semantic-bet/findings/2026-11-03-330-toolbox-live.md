# The `custom-toolbox` arm live: an ADK agent on generated MCP Toolbox tools only (#330)

Question (Q5, live part): how far can generated MCP Toolbox tools over the `native-shaped` arm's seven table functions go, and what falls outside their shapes?
The offline part (the generator, Toolbox offline, the frozen set's fit to the tools' shapes) is [#344's finding](2026-11-03-344-toolbox-shapes.md).

- By hand: 5 right, 3 declined, 2 confident-wrong of 10; on #328's seven: 4 right, 1 declined, 2 confident-wrong, where `native-mcp` got 7 of 7.
  One run each, so a shape, not a rate.
- Every exact or derived verdict #344 gave came out right except `average_order_value`; every `out` verdict came out declined except `return_rate_september`: #344's reading of the shapes predicted the agent's route in 8 of 10.
- The two confident-wrong answers both came from a governed tool used at the wrong grain or definition, the failure a semantic layer is meant to remove:
  - `return_rate_september`: returns are dated by the return, so the September window of `returns_by_reason` and `damaged_returns_daily` answered "The query returned 0 rows." and `net_sales_daily`'s `returns_count` was null every day; the agent reported 0% with full confidence.
  - `average_order_value`: `daily_sales.orders_total` counts cancelled orders (the trap #329's finding names); the agent divided revenue by it, after asking itself whether cancelled orders belong and deciding they do.
- The agent read the tools' descriptions well enough to decline the right cases: `bet_customers_september` (non-additive per-day counts, the trap #344 named) and `net_revenue_germany` (no tool has both country and returns) were declined with the reason.
- **The scorer misread two of ten answers**: the free model's reasoning comes back inside the answer text (as in #328 and #346), and `bet_rule` reads that text whole.
  `bet_customers_september` scored right because the reasoning lists day numbers ("Days 1, 4, 7, 10, …") that include the expected `10`, though the final answer declines; `median_order_value` scored wrong because the reasoning's numbered tool list (`1.` … `7.`) counts as stated numbers beside a decline.
  Filed as [#351](../../../../../../issues/351), before #333, which scores every arm with the same rule.
  The cause (#351, 2026-11-03T09:07Z): ADK marks the reasoning as `thought` parts, and the probes' `ask()` kept them; it now keeps them apart (`thought` in each row), as the eval's own extractor already did (`evaluation.py`'s `_text`).
  Rerun with the fix into a scratch log: `median_order_value` scored declined; `bet_customers_september` said "I cannot provide …", outside the rule's decline list, which now holds `cannot provide | determine | compute | calculate` (a unit test with that answer), so it scores wrong (a decline beside a figure), not confident-wrong.
- Toolbox needed nothing beyond the generated file: no ADC on the host (the source builds its client per call from the header), the `McpToolset` listed all seven tools, and every call answered in about 2 s.

## What it means for the verdict

- **Q5: generated Toolbox tools work as a front door and fail where their shape stops.** On the cases their shapes fit, the agent answered right (5 of 6 by hand); on the cases outside, it declined three times and improvised confidently once.
  Against `native-mcp` on the same seven cases (7 of 7, #328), this arm is weaker on exactly the traps that need a definition the tools don't carry (return rate by order date, AOV without cancelled orders), because a tool serves rows, not the metric's definition.
- The confident failures come from the tools being governed: a table function named for the business's metrics returns a column (`orders_total`) whose meaning the agent cannot see, so it trusts it; a description listing each column's definition, or a tool per metric that returns the metric itself (`average_order_value`), would close both cases, which is #344's point that a shipping form needs MetricFlow's query API, not saved statements.
- What `useClientOAuth` adds holds live: the caller's token reaches BigQuery and nothing else does; a client with no token gets nothing, on HTTP as on stdio.
  At work that makes row policies (#332) apply per user with no code of ours; here the token was the automation account's.
- Toolbox has no byte cap of its own: fixed statements bound the cost, so a generated tool must never take free-form SQL or a table name as a parameter.

## Still unknown

- Rates: one run per case on ten cases; the frozen set with k runs beside the other arms is #333's, and needs the scorer fix (#351) first.
- Whether richer generated descriptions (each output column with its definition, units and grain) turn the two confident-wrong cases into right or declined ones; not run.
- An end user's token through `useClientOAuth` (only the automation account's here), and how Toolbox behaves with a token BigQuery refuses.
