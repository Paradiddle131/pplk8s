# Case sweep for test defects (#437)

## Method

I read the three sets (`services/semantic-agent/evals/semantic_bet.yaml`, `semantic_bet_hard.yaml`, `semantic_bet_hard_v2.yaml`), each case's expected numbers in `expected.json`, the case rows of `redacted.jsonl` (24 cases already retired, skipped here), and RULE.md § Retiring a defective case and § Scoring a run.
I read the governed definitions: the metrics, labels and glossary in `dbt/models/silver/schema.yml` and `dbt/models/semantic/semantic.yml`, the legacy models in `dbt/models/legacy/`, and the BigQuery verified queries in `findings/2026-11-03-357-verified-queries.json`.
I checked numbers on the fixture warehouse (`dbt_dev`) with read-only SELECTs: ties, alternative readings, each `naive_sql` and `legacy_sql`, and each legacy table's obvious query against the expected number.
I read `bet_rule.at_risk` to see how the scorer treats small numbers: a whole number of 40 or less, or one the question holds, stands only as the answer's first figure, else the blind judge decides.
I never opened any eval log, scored run, result, judge verdict, report, brief or other finding about the arms, and judged each case on the case alone.
The 130 cases checked are the 76 unretired frozen cases, the 40 unretired cases shared by hard and hard-v2 (one row each; their questions and expected SQL are byte-identical in both files), and the 14 unretired cases new in hard-v2.

## The legacy tables (pattern 4)

`hard_real_revenue`'s net reading is confirmed: `select sum(net_revenue) from legacy.daily_net_sales where sales_date between '2026-10-01' and '2026-10-10'` returns 2047.59, the expected number.
It is not a case defect: `legacy.daily_net_sales` equals `exposed.net_sales_daily` on every row of the fixture (a full join on the date with `net_revenue is distinct from net_revenue_eur` returns no row), because no return falls on a day without orders.
`legacy.channel_daily` likewise equals `exposed.channel_performance_daily` in spend, leads and bookings on every row (the same full join returns no row), so any sum-over-sum channel case gives the expected number from it.
`legacy.country_sales` differs only where cancelled orders fall: `revenue_germany` (379.75) matches it, every other country case does not.
So on this fixture a deprecated table gives the right number for every net-revenue and channel case, by the fixture's construction; RULE.md counts that as no defect (the number is right), and only `distractor` cases depend on a difference, where the one remaining distractor (`bet_top_country_september`) holds (2857.00 against 2665.50).
A later set version that wants to test legacy avoidance needs a return dated on a day without orders, or a channel row the legacy query drops.
