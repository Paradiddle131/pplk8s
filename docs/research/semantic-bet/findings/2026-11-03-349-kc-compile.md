# What Knowledge Catalog's `compile_query` and `execute_query` accept (#349)

Question (Q1, Q3): the catalog's MCP server advertises `compile_query` / `execute_query` over "a Knowledge Catalog semantic model"; do they accept a dbt-imported semantic model, and if not, what do they accept?
#326 saw every `compile_query` call fail at 07:43Z; #328's agent reached for both unprompted at 08:10Z and got the same error.

## What was run

- 2026-11-03T08:48Z, read-only: [`probes/326_kc_readback.py`](../probes/326_kc_readback.py) again (its last line is a `compile_query` call).
- 08:49Z, read-only: [`probes/349_kc_compile.py`](../probes/349_kc_compile.py), on the proxy-injected credential: the server's `tools/list` (the two tools' descriptions and input schemas printed whole), then `compile_query` over nine requests in each of the locations `us` and `global`, each differing from the first in one respect: `modelEntry` as the full entry name, the bare entry id, the dbt fully qualified name (`dbt:semantic_model:pplk8s-lab-001.pplk8s.orders`) and a BigQuery table's entry (`governed.orders_daily` in `@bigquery`); fields as dbt names (`order__status`, `orders_total`), as Looker-style `view.field` names, and one metric (`revenue_eur`); a request with no `fields`, one with no `modelEntry`, and one with `rowLimit` as a string.
  The raw output is [`2026-11-03-349-kc-compile.txt`](2026-11-03-349-kc-compile.txt).
  `execute_query` was not called: it runs a BigQuery job, and the issue gates it on a compiled query to dry-run first.
- Docs read 2026-11-03 (`stated`): the Knowledge Catalog MCP reference, the dbt import page, and Google's 2026-10-29 post on semantic model support (Sources).

## What was observed

`measured` (the runs above):

- The readback's `compile_query` on `semantic_model_pplk8s_orders`: `An internal error has occurred (873839cb-…)`, as at 07:43Z; the rest of the readback is unchanged (`lookup_context` 15,999 characters, the same search hits).
- `tools/list`: still 17 tools, and `compile_query` / `execute_query` read as #326 copied them: "Compiles a query against a Knowledge Catalog semantic model into SQL, without running it … Prefer this tool over writing raw SQL when a semantic model covers the question … Compilation reads no table data and always returns the same SQL for the same request"; `execute_query` "runs as the caller … BigQuery bills it to the project".
  Both require `projectId`, `location`, `modelEntry` and `fields`, and take `filters` (`field`, `expression`), `sorts` (`field`, `descending`) and `rowLimit`; `execute_query` adds `bigquery` (`maximumBilledBytes`, `datasetId`).
- `compile_query`, 18 calls: 16 answered `isError: true`, `An internal error has occurred (<uuid>)`, each with its own uuid, whatever the entry, the field names or the location, **including the request with no `modelEntry` at all**, which the schema marks required.
  The two with `rowLimit: "ten"` answered `Request contains an invalid argument.`
- So the server checks argument types and nothing else before failing: a missing required argument and a nonexistent entry reach the same internal error as a real dbt semantic model, which places the failure in the backend behind the tool, before it reads the request's content.

`stated` (read 2026-11-03):

- The [Knowledge Catalog MCP reference](https://docs.cloud.google.com/dataplex/docs/reference/mcp) names `search_entries`, `lookup_context` and `lookup_entry` on `/mcp` and the data-products tools on `/mcp/data-products`; neither `compile_query` nor `execute_query`, and no "semantic model" entry type.
- The [dbt import page](https://docs.cloud.google.com/knowledge-catalog/docs/dbt-transfer) imports semantic models, metrics and saved queries "for discovery and context" and names no way to query them.
- [Google's post of 2026-10-29](https://cloud.google.com/blog/products/data-analytics/expanded-semantic-model-support-in-knowledge-catalog) makes semantic-model ingestion GA from LookML, BigQuery Graph measures, dbt MetricFlow, Snowflake, Databricks and SAP CSN, and says agents apply "the exact metric formula" through "a single context query"; it names no compile or query API, and Knowledge Studio stays in preview.
- A web search for the two tools found no page that names them.

## What it means for the verdict

- **Still unknown whether they accept a dbt semantic model**, and now better bounded: the tools are deployed and advertised to every agent that lists the server, undocumented, and fail in the backend for any request, so nothing on our side (entry name form, field naming, location, the IAM grants) can make them work today.
- "A Knowledge Catalog semantic model" in their description is most likely the entry type the GA ingestion creates from every source (dbt's included): the tool takes any `modelEntry`, and the post calls all six sources' imports semantic models.
  That is a reading, not a measurement; if it holds when the backend ships, Google's MCP server compiles dbt metrics to SQL with no code of ours, and the bet's gap (Q11) closes on Google's side.
- Until then, the agents that answered right through the catalog (#328) did so by reading definitions and writing SQL, not by compiling: the semantic query stays ours to provide.
- An agent offered these tools pays for them: #328's agent spent four calls on them before writing SQL; a production agent should filter them out until they work.

## Still unknown

- What the tools accept once the backend answers, and when that is; the watch (#335) now retries one `compile_query` a day ([`watch.md`](watch.md)).
- Whether an entry made another way (a context set, a LookML import) works where the dbt entries fail: not tried, since every request fails before the entry is read, and LookML is out of scope.
