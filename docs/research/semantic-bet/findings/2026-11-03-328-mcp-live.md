# The `native-mcp` arm live: an ADK agent on Google's BigQuery and Knowledge Catalog MCP servers only (#328)

Question (Q3): can an ADK agent built only on Google's managed MCP servers answer through the metric definitions Knowledge Catalog imported from our dbt project (#326)?
The offline part (the agent, a local stand-in, the cost guard) is [#346's finding](2026-11-03-346-mcp-offline.md).

- 7 of 7 right, six of them traps where the obvious SQL gives another number; one run each, so a shape, not a rate.
- The catalog was the agent's map every time: each case began with `search_entries` and read `lookup_context` before any SQL; in three cases the context it read was a dbt metric or semantic model the import created, and the answers followed their definitions (`cost_per_booking_total`: "per the definition of total spend over total bookings for the period, not an average of daily ratios").

- The model's reasoning came back inside the answer text in every case (the free model's habit, also seen in #346).
- The guard refused nothing: every query's dry run through the MCP tool reported `totalBytesProcessed` under 10 MiB, which also answers #346's open question (the MCP dry run reports it, as the REST API does).

## What it means for the verdict

- **Q3: yes, with a caveat that matters.** An agent built only from Google's MCP servers and an off-the-shelf ADK loop found and followed our metric definitions and gave the right number on every probe, traps included, where the data agent of #327 never touched the imported metrics.
  The difference is who reads the catalog: here the agent calls `search_entries` and `lookup_context` itself.
- **But the number came from our governed tables in five of seven cases**: the dbt-built `governed.*` tables (#310) carry most of the metric logic already, so this arm measures "Google's MCP servers over a warehouse that already holds governed tables", not Google's stack alone.
  The two cases over `silver` show the agent can also turn an imported definition into correct SQL (a ratio of sums, a status filter).
- **The semantic query itself is still ours to provide**: Google's `compile_query` / `execute_query` exist and are offered to the agent, which reached for them unprompted, and they fail on dbt-imported semantic models today; the day they work, this arm becomes a semantic-layer agent with no code of ours, which is the fact most likely to change the verdict (the watch, #335).
- The cost guard is the one piece of our code this arm needs: Google's `execute_sql_readonly` takes no byte cap.

## Still unknown

- Rates: one run per case on seven cases; the frozen set with k runs and the other arms side by side is #333's.
- The same agent with the governed tables hidden (only `silver` and the catalog): whether the definitions alone keep it right; not run.
- "Before the import": the issue asked for answers before and after #326; the import landed before this run, so only the stand-in's technical-metadata run (#346) stands for "before", on another warehouse.
- Whether `compile_query` / `execute_query` accept dbt-imported semantic models when they work, or only Looker's.
