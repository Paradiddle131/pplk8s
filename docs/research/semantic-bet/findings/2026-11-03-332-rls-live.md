# Row policies through views, table functions and an authorized table function, live (#332)

Question (Q7): does a row access policy filter rows read through a view, a table function and an authorized table function; does a data agent over such a view keep conversation logging, and what does a logged turn hold?
The offline part, with the docs read and the emulator's refusal, is [#345's finding](2026-11-03-345-rls-offline.md).

## What was run

- 2026-11-03T07:00Z and 07:02Z, live on `pplk8s-lab-001`, the same command twice (the first run's output was cut by the session, the second kept): `GCP_PROJECT=pplk8s-lab-001 bash docs/research/semantic-bet/probes/332_rls_check.sh`.
  It runs `make gcp-cost-check` and `make gcp-usage-check` (ok before and after both runs: $0.000010 this month, BigQuery queries at 5.2 % of the free tier), checks `bigquery.rowAccessPolicies.create` with `testIamPermissions` (held), dry-runs each statement of [`probes/332_bet_rls.sql`](../probes/332_bet_rls.sql) and runs it capped at 10 MiB: datasets `bet_rls` and `bet_rls_api` (US); `bet_rls.orders` with six rows (DE 10, 20, 30; FR 40, 25; US 25); the view `orders_v`, the table function `orders_tf` and, in the other dataset, the authorized table function `orders_auth_tf`; the policy `bet_de`, `GRANT TO` the caller (`pplk8s-automation@…`) `FILTER USING (country = 'DE')`; then one count and sum per path.
- 07:04Z: [`probes/332_logging_check.py`](../probes/332_logging_check.py) published the data agent `projects/pplk8s-lab-001/locations/us/dataAgents/bet-rls` over `bet_rls.orders_v` with `bigqueryAgentAnalyticsEnabled` and `bigqueryAgentAnalyticsTable` (`agent_logs.data_agent_conversations`) through `publish.py`'s publisher, read it back, asked "What is the total order amount by country?", and looked for the log table.

## What was observed (`measured`, the runs above)

```text
caller: pplk8s-automation@pplk8s-lab-001.iam.gserviceaccount.com
{"permissions": ["bigquery.rowAccessPolicies.create"]}
Created row access policy bet_de on table pplk8s-lab-001.bet_rls.orders
{"path": "authorized table function", "n": "3", "amount": "60"}
{"path": "table", "n": "3", "amount": "60"}
{"path": "table function", "n": "3", "amount": "60"}
{"path": "view", "n": "3", "amount": "60"}
```

- The policy held on every path: 3 rows and 60 (the DE rows) through the table, the view, the table function and the authorized table function, against 6 and 150 without it (the emulator's run in #345).
  The authorized table function lives in another dataset and is authorized on `bet_rls`, so it reads without table-level access, yet it kept the caller's row filter: authorization lifts table permissions, not row policies.
- The data agent over the view ran as the caller and saw only the policy's rows: its SQL `SELECT country, SUM(amount) … FROM bet_rls.orders_v GROUP BY country`, its rows `[{country: DE, total_amount: 60}]`, its answer "The total order amount for Germany (DE) is €60.00."; no `Access Denied`, since the caller is the policy's grantee.
- Conversation logging did not stick: the create took both fields without error, and a GET returned neither (`bigqueryAgentAnalyticsEnabled` absent, `bigqueryAgentAnalyticsTable` null); `agent_logs.data_agent_conversations` does not exist ("Not found: Table"). This is #207's 2026-11-02 observation again, on a new agent.

## What it means for the verdict

- Table functions and authorized table functions are safe carriers for row-scoped metrics: the shaped arm (#329) and generated Toolbox tools (#330) keep a caller's row policy without views in between, now measured rather than assumed (the docs still state it for views only).
- The privacy question #345 raised (a view passes the logging check, so row-scoped answers could be logged) can't be measured on this project while the API drops the logging fields outside the Agent Analytics preview; it stays a stated risk with a documented mechanism.

## Still unknown

- What a logged turn holds for a row-scoped answer read through a view, and whether the logging check inspects table functions: gated on the preview (`semantic/PLAN.md` § 6).
- A second identity outside the policy (it would read 0 rows, or be refused): one identity was enough to see whether each path filters, so this wasn't run.
