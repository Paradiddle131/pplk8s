# dbt-mcp on the lab's project with no dbt platform account (#334, part 1 of 2)

Question (Q9, dbt-mcp half): what does dbt Labs' MCP server give a team on our project for free, and what needs the dbt platform?
Lightdash, the other half, is [its own finding](2026-11-03-334-lightdash.md).

## What was run

- 2026-11-03T00:45Z, offline, the Compose warehouse up (`make services-up`, empty): [`probes/334_dbt_mcp.py`](../probes/334_dbt_mcp.py) with `dbt-mcp==2.7.0` (Apache-2.0, released 2026-10-09; Python 3.12 or 3.13 only) over stdio, `DBT_PROJECT_DIR` a copy of `dbt/` with its packages, `DBT_PATH` dbt Core 1.12.6 with `dbt/requirements-postgres.txt`, no `DBT_HOST` and no token.
- The probe lists the tools, then calls `list`, `compile`, `show`, `list_metrics`, `query_metrics`, `get_all_models`, `get_mart_models`, `get_metrics_compiled_sql`, `get_lineage_dev` and `get_node_details_dev`.

## What was observed (`measured`, the run above)

- 50 tools are listed with no platform account, the platform ones included; an agent sees them all and learns which work only by calling them.
- Work: `list` (every node, metrics and saved queries included), `compile` (`OK`), `show` (runs the agent's own SQL on the warehouse), `get_lineage_dev` (from the local manifest: `metric.pplk8s.revenue_eur` ← `semantic_model.pplk8s.orders` ← `model.pplk8s.slv_orders` ← `brz_synthetic_orders` ← the source; children include `revenue_eur_mtd` and three saved queries), `get_node_details_dev` (the model's description, columns and tests).
- Fail, each with `DBT_HOST is a required environment variable`: `list_metrics`, `query_metrics`, `get_metrics_compiled_sql`, `get_all_models`, `get_mart_models`; the server logs `Could not resolve credentials — defaulting to single-project mode`.
- `show` reported `is_error: false` on a failed query: the result text holds dbt's `Database Error ... relation "silver.orders" does not exist` (the empty warehouse), so a caller has to read the text to know.
- `dbt parse` on dbt 1.12.6 writes `target/osi_document.json` (OSI 0.1.1, one dialect `ANSI_SQL`): 16 datasets, 27 relationships, 52 of the project's 57 metrics.
  Left out: the 4 conversion metrics (`lead_to_booking_rate`, `view_to_cart_rate`, `cart_to_checkout_rate`, `signup_to_first_order_rate`) and the natural entity `candidate`, each with a warning, and `median_order_value_eur`, the approximate median, with none.
  Kept with a warning that their meaning is lost: the 6 cumulative metrics (`bookings_mtd`, `customers_to_date`, `engaged_customers_7d`, `engaged_customers_28d`, `leads_mtd`, `revenue_eur_mtd`).

## As documented (`stated`, [About dbt MCP](https://docs.getdbt.com/docs/dbt-ai/about-mcp), read 2026-11-03)

- The self-hosted server works "with local dbt projects with or without a dbt platform account"; the platform adds "Semantic Layer, Discovery API, Admin API, SQL, Codegen".
- "Access to the dbt APIs is limited depending on your plan type"; the remote MCP server is on all plans, its tools depend on the plan, and it runs no CLI commands.

## What it means for the verdict

- Without the dbt platform, dbt-mcp gives an agent the project's metadata and an open SQL door (`show`), not the metrics: no tool answers through a metric's definition, so free dbt-mcp has the shape of the `baseline` arm (text-to-SQL over documentation), not of `custom-metricflow`.
- Borrow, don't adopt: the `_dev` lineage and node tools are what an agent needs to explain a number's provenance, and they read only the local manifest.
- The OSI export is lossy exactly where business metrics are hard (conversion, cumulative, percentile): anything that grounds an agent through OSI, or through a catalog that maps to it, loses those metrics' meaning; this is a check for #326 (does Knowledge Catalog keep them?) and #335 (Ossie's format moving).
