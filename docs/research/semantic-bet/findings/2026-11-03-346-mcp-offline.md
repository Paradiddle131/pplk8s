# The `native-mcp` arm's ADK agent, built and run offline against a local MCP stand-in (#346, for #328)

Question (Q3, offline part): can an ADK agent whose only tools are Google's BigQuery and Knowledge Catalog MCP servers be built so that #328's live step is one command, and what does it do with technical metadata alone?
The live part (Google's endpoints, before and after the dbt import) waits on the cost check ([#338](../../../../../../issues/338)) and on #326.

## What was run

- 2026-11-03T05:44Z, the tools' docs read (below).
- [`probes/328_mcp_agent.py`](../probes/328_mcp_agent.py): the agent (ADK 2.13.0, two `McpToolset`s over streamable HTTP, filtered to the read-only tools; the model `nvidia/nemotron-3.5-super-vl:free` through OpenRouter, the repo's default).
- [`probes/328_mcp_standin.py`](../probes/328_mcp_standin.py): a local stand-in serving the same tool and argument names over the Compose warehouse's `dbt_dev` (the agents' fixture, `tests/e2e/agent-fixture.sh`), SQL as the baseline's read-only `agent_sql` role, `lookup_context` from the dbt catalog's technical metadata (what Knowledge Catalog holds before the import).
- [`probes/328_standin_check.sh`](../probes/328_standin_check.sh), three times between 05:46Z and 05:49Z (the stand-in made tolerant of GoogleSQL quoting and of malformed entry names between runs; the third run is quoted): tool discovery, the cost guard, and the frozen case `revenue_one_day` ("How much revenue did we make on 2 October 2026?", expected 868.65).
  About 20 free-tier model requests in all.

## What the docs say (`stated`, read 2026-11-03)

- BigQuery's server, `https://bigquery.googleapis.com/mcp`, streamable HTTP, OAuth scope `bigquery`, roles `mcp.toolUser`, `bigquery.jobUser`, `bigquery.dataViewer`; six tools, `execute_sql` the only one that writes ([use the BigQuery MCP server](https://docs.cloud.google.com/bigquery/docs/use-bigquery-mcp), [reference](https://docs.cloud.google.com/bigquery/docs/reference/mcp)).
- `execute_sql_readonly` takes `projectId`, `query`, `dryRun`, `labels`, `jobTimeoutMs`, `timeoutMs`, and no `maximumBytesBilled` ([its schema](https://docs.cloud.google.com/bigquery/docs/reference/mcp/tools_list/execute_sql_readonly)): a query through Google's MCP server can't carry the per-job cap the $0.00 rule asks for.
- Knowledge Catalog's server, `https://dataplex.googleapis.com/mcp`: `search_entries`, `lookup_context`, `lookup_entry`; a second toolset at `/mcp/data-products` with writes ([reference](https://docs.cloud.google.com/dataplex/docs/reference/mcp)).
  `lookup_context` takes `projectId`, `location` and up to 10 entry names, "usually" from `dataplexEntry.name` of a `search_entries` result, and returns one `context` string, "usually YAML" ([its schema](https://docs.cloud.google.com/knowledge-catalog/docs/reference/mcp/tools_list/lookup_context), [search_entries](https://docs.cloud.google.com/knowledge-catalog/docs/reference/mcp/tools_list/search_entries)).

## What was observed (`measured`, the runs above)

- Discovery and filter: the agent sees exactly `execute_sql_readonly`, `get_table_info`, `list_dataset_ids`, `list_table_ids`, `lookup_context`, `search_entries` (the stand-in serves no `get_dataset_info` or `lookup_entry`; the filter names them for the live servers).
- The cost guard (a `before_tool_callback`, the one piece of our code): it rewrote `projectId: someone-elses-project` to `pplk8s-lab-001`, let a query run when the dry run reported 0 bytes, and refused it at 99,999,999,999: `refused: the query would process 99999999999 bytes, over 10485760`.
- The answer, all three runs: the agent searched "revenue", picked `exposed.net_sales_daily` (described as "Daily revenue net of partner returns"), and headlined net revenue: "On 2 October 2026, net revenue was **861.40 EUR** (revenue of 868.65 EUR minus returns of 7.25 EUR)"; the frozen case expects `revenue_eur`, 868.65.
  The model's reasoning ("The table's description says ... so the primary revenue metric is `net_revenue_eur`") came back as part of the answer text.
- `lookup_context` was called with `bigquery:pplk8s-lab-001.exposed.net_sales_daily` (the `fullyQualifiedName`) in runs 2 and 3, and with a truncated name in run 1, never with the entry name; the first stand-in read run 1's name loosely and answered, run 2's crashed it, and the third refused it (its message is ours, the real server's is unknown), after which the agent fell back to `get_table_info`.
- GoogleSQL quoting (backticks, `pplk8s-lab-001.exposed...`) failed on the stand-in's PostgreSQL until the stand-in stripped it; on BigQuery it is correct.

## What it means for the verdict

- The native arm is buildable with no tool of ours, but not inside the $0.00 rule as Google ships it: the cap has to live in the agent (a dry-run guard like this one, or a custom per-user query quota, an owner's change), which is the kind of guardrail a team would write themselves; that is a small, real gap.
- Technical metadata alone steers the agent to the table whose description best matches the word, not to the defined metric: with only descriptions, "revenue" became net revenue; this is the failure Q2 and Q3 ask whether the imported MetricFlow definitions fix.
- Whether the agent reaches the imported metric at all depends on `lookup_context` getting entry names: this agent passed the wrong form three times out of three, so the live run should record every `lookup_context` call and its answer, and a refusal there is part of the finding, not noise.

## Still unknown

- What Google's servers answer to the same calls: the tools' own descriptions (the stand-in's are shorter), `lookup_context`'s answer to a non-entry name, the context's content before and after the import (#328 live, after #326 and #338).
- Whether the guard's dry run through the MCP tool reports `totalBytesProcessed` as the REST API does (the schema says it does).
