## What the data agents' loop calls

- `stated`: the chat stream's system messages are `text` (`THOUGHT`, `PROGRESS`, `FINAL_RESPONSE`, `FOLLOWUP_QUESTIONS`), `schema` (query, result), `data` (`query`, `generatedSql`, `result`, `bigQueryJob`, `matchedQuery`), `analysis` (Python: `code`, `executionOutput`), `chart`, `error` and `exampleQueries` ([the v1 `Message` reference](https://docs.cloud.google.com/gemini/docs/conversational-analytics-api/reference/rest/v1/Message), read 2026-11-06).
- `measured`, 7 fresh chats (`findings/2026-11-06-388-data-agent-streams.jsonl`, raw streams kept): `native-bare` on `hard_top_channel_bookings`, `hv2_median_gap_between_orders`, `hv2_signups_never_ordered`; `native-context-bare` on `hv2_median_gap_between_orders`, `hv2_top_three_customers_share`; `native-kc-max` on `hv2_median_customer_spend`, `hard_top_channel_bookings`.
  Every chat streamed exactly one `data.query`, one `generatedSql`, one `bigQueryJob` and one `result`, four to eight `THOUGHT`s, a final answer and follow-up questions; no `schema`, `analysis`, `chart` or `error` message.
  So the loop's only figure source is SQL it writes and BigQuery runs, which the logs' `generated_sql` carries.
- `measured`, every run: each of the 6,969 `generated_sql` calls in the 27 data-agent logs is a BigQuery job the same agent ran (`INFORMATION_SCHEMA.JOBS_BY_USER`, label `data-agent-id=<agent>`, matched on the query text with whitespace removed): 100% on every log.
  The other way, 1,165 of the agents' 6,275 jobs since 2026-11-03 are in no eval log; by their timing and text these are canaries (unlogged by design), runs whose chat failed and was asked again, earlier probes' checks (`bet-nokc`, `bet-rls`, the main track's agents) and `bet-shaped`'s parameterised verified queries; labels alone cannot attribute each job to a run, which stays unknown.
- Every agent job was a `SELECT`; their bytes billed sit inside the daily fence the usage check reads.

The jobs query (read-only, under 70 MB, `--maximum_bytes_billed`):

```sql
SELECT (SELECT value FROM UNNEST(labels) WHERE key = "data-agent-id") AS agent,
       CONCAT(r.dataset_id, ".", r.table_id) AS t, COUNT(*) AS n
FROM `region-us`.INFORMATION_SCHEMA.JOBS_BY_USER, UNNEST(referenced_tables) AS r
WHERE creation_time > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 5 DAY)
  AND EXISTS (SELECT 1 FROM UNNEST(labels) WHERE key = "ca-bq-job")
GROUP BY 1, 2
```

- Cloud Logging holds only the agents' admin writes (`CreateDataAgent` 36, `UpdateDataAgent` 60 in 4 days); the chats' data-access logs are off, and the `agent_logs` dataset holds no table: neither can show a run's steps, the jobs table can.
- `JOBS_BY_PROJECT` is refused to the lab's credential (`bigquery.jobs.listAll`); `JOBS_BY_USER` sees every job, since every pass ran as the same service account.

## Two harness differences found while mirroring `native-mcp` (2026-11-06T18:40Z)

- Google's servers list 14 of the arm's 16 names, today as on 2026-11-04 (`compile_query` and `execute_query` are not listed), so `cc-native-mcp`'s run is held to the 14 served, each of them one of the 16 (`probes/387_cc_strict.py`, `served`).
- Google marks `list_entries` and `get_glossary` `_meta.ui.visibility: ["app"]` (an MCP Apps hint: shown to the app, not the model). Claude Code honours it and hid both from the model (its debug log: "kept from the model (its _meta.ui.visibility omits "model")"); ADK ignores it, so the `native-mcp` arm's model was offered both. The guard (`probes/387_mcp_guard.py`) lists the tools without that hint, so the mirror offers the model the same 14 tools the arm's model had; names, descriptions and schemas are Google's, unchanged.
