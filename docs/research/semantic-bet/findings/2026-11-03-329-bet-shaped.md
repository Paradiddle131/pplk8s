# The `native-shaped` arm's table functions, built offline (#329, part 1)

Question (Q4, offline part): can every dbt saved query become a BigQuery table function with a date range, written from MetricFlow's compiled SQL, and do those functions give the right numbers?
The live part (the `bet_shaped` dataset on the lab project, whether `bqRoutines` takes a table function, and what the data agent uses) waits on the cost check ([#338](../../../../../issues/338)).

## What was run

- 2026-11-03T01:57Z, offline: [`probes/329_shaped_sql.py`](../probes/329_shaped_sql.py) compiles the 7 saved queries in `dbt/models/semantic/saved_queries.yml` with MetricFlow's engine (dbt-metricflow 0.15.0, dbt-bigquery 1.12.1, the compile-only `bigquery` target) and a sentinel time constraint, 2026-02-03 to 2026-04-05.
- [`probes/329_bet_shaped.sql`](../probes/329_bet_shaped.sql): one `CREATE OR REPLACE TABLE FUNCTION bet_shaped.<saved query>(start_date DATE, end_date DATE)` per saved query, written once from that SQL by a one-off edit read back by hand: the sentinel range became `DATE(<day>) BETWEEN start_date AND end_date`, relations lost their project, comments dropped; the description holds the saved query's description and question.
- 2026-11-03T01:59Z, offline: [`probes/329_emulator_check.sh`](../probes/329_emulator_check.sh) creates them on the lab's BigQuery emulator (`ghcr.io/goccy/bigquery-emulator:0.8.1`) over 16 hand-made silver rows whose right answers are written in the probe, and calls each for February and March 2026.

## What was observed (`measured`, the runs above)

- MetricFlow puts the date range in every input, not once: 3 WHERE clauses for `daily_sales`, `net_sales_daily` and `channel_performance`, 2 for `sales_by_country_daily`, 1 for the other three; `channel_performance` filters spend, leads and bookings separately, then joins them on channel.
  A hand-written function, or an agent's own SQL, that filters only one input gives cost per lead over mismatched periods.
- MetricFlow moved a start before its time spine forward: a 1999-01-01 start compiled as `BETWEEN '2000-01-01' AND '1999-12-31'` (an empty range, no warning), so the sentinels sit inside the spine.
- The compiled SQL is 20 to 141 lines per saved query; `net_sales_daily` and `channel_performance` are full outer joins of per-metric CTEs (3 and 6 joins).
- On the emulator all 7 functions are created and return the right answers, for example `net_sales_daily` 2026-02-10: revenue 100, 2 returns, 13.5 returned, net 86.5; `channel_performance` search: spend 40, 2 leads, 1 booking, 20 a lead, 40 a booking; the May and June rows fall outside.
- Side finding: MetricFlow's `CLIConfiguration.setup`, which the `mf` CLI and `dbt/scripts/build_catalog.py` use, runs dbt's connection test (`select 1 as id`) before any explain; on this cloud VM the egress proxy injects a Google credential, so the "compile-only" target's placeholder token reached BigQuery and was refused (`Not found: Project pplk8s-lab`): nothing ran or billed, but the compile is not offline here (filed as its own issue).

## What it means for the verdict

- The shaped arm is cheap to build by hand: seven functions, all of MetricFlow's logic kept, each a single call with two dates; whether a data agent calls them is the live question.
- The date range landing in every input is the concrete trap a function removes: it is what a model writing its own SQL over `channel_performance`'s three facts is likely to get wrong, and what #333 can score.
- A function fixes the group-bys of its saved query: questions outside the seven shapes still fall to the agent's own SQL (Q5 asks how far generated tools go).
