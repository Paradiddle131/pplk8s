# The `native-shaped` arm: table functions and verified queries, offline and live (#329)

Question (Q4): can every dbt saved query become a BigQuery table function with a date range, written from MetricFlow's compiled SQL, and do those functions give the right numbers (part 1, offline)?
Does a data agent's `userFunctions.bqRoutines` take a table function, and does an agent offered the functions and parameterised verified queries use them instead of its own SQL (part 2, live, [below](#part-2-live-on-the-lab-project-2026-11-03))?

## Part 1, offline

### What was run

- 2026-11-03T01:57Z, offline: [`probes/329_shaped_sql.py`](../probes/329_shaped_sql.py) compiles the 7 saved queries in `dbt/models/semantic/saved_queries.yml` with MetricFlow's engine (dbt-metricflow 0.15.0, dbt-bigquery 1.12.1, the compile-only `bigquery` target) and a sentinel time constraint, 2026-02-03 to 2026-04-05.
- [`probes/329_bet_shaped.sql`](../probes/329_bet_shaped.sql): one `CREATE OR REPLACE TABLE FUNCTION bet_shaped.<saved query>(start_date DATE, end_date DATE)` per saved query, written once from that SQL by a one-off edit read back by hand: the sentinel range became `DATE(<day>) BETWEEN start_date AND end_date`, relations lost their project, comments dropped; the description holds the saved query's description and question.
- 2026-11-03T01:59Z, offline: [`probes/329_emulator_check.sh`](../probes/329_emulator_check.sh) creates them on the lab's BigQuery emulator (`ghcr.io/goccy/bigquery-emulator:0.8.1`) over 16 hand-made silver rows whose right answers are written in the probe, and calls each for February and March 2026.

### What was observed (`measured`, the runs above)

- MetricFlow puts the date range in every input, not once: 3 WHERE clauses for `daily_sales`, `net_sales_daily` and `channel_performance`, 2 for `sales_by_country_daily`, 1 for the other three; `channel_performance` filters spend, leads and bookings separately, then joins them on channel.
  A hand-written function, or an agent's own SQL, that filters only one input gives cost per lead over mismatched periods.
- MetricFlow moved a start before its time spine forward: a 1999-01-01 start compiled as `BETWEEN '2000-01-01' AND '1999-12-31'` (an empty range, no warning), so the sentinels sit inside the spine.
- The compiled SQL is 20 to 141 lines per saved query; `net_sales_daily` and `channel_performance` are full outer joins of per-metric CTEs (3 and 6 joins).
- On the emulator all 7 functions are created and return the right answers, for example `net_sales_daily` 2026-02-10: revenue 100, 2 returns, 13.5 returned, net 86.5; `channel_performance` search: spend 40, 2 leads, 1 booking, 20 a lead, 40 a booking; the May and June rows fall outside.
- Side finding: MetricFlow's `CLIConfiguration.setup`, which the `mf` CLI and `dbt/scripts/build_catalog.py` use, runs dbt's connection test (`select 1 as id`) before any explain; on this cloud VM the egress proxy injects a Google credential, so the "compile-only" target's placeholder token reached BigQuery and was refused (`Not found: Project pplk8s-lab`): nothing ran or billed, but the compile is not offline here (filed as its own issue).

### What it means for the verdict

- The shaped arm is cheap to build by hand: seven functions, all of MetricFlow's logic kept, each a single call with two dates; whether a data agent calls them is the live question.
- The date range landing in every input is the concrete trap a function removes: it is what a model writing its own SQL over `channel_performance`'s three facts is likely to get wrong, and what #333 can score.
- A function fixes the group-bys of its saved query: questions outside the seven shapes still fall to the agent's own SQL (Q5 asks how far generated tools go).

## Part 2, live on the lab project (2026-11-03)

### What was run

- 06:39Z: `make gcp-cost-check` (ok, $0.000010 this month under the accepted $1.00) and `make gcp-usage-check` (ok).
- 06:40Z: `bq query --dry_run` of [`probes/329_bet_shaped.sql`](../probes/329_bet_shaped.sql) (valid, 0 bytes), then the script: dataset `bet_shaped` in `US` and its seven table functions on `pplk8s-lab-001`; each called for 2026-08-01 to 2026-10-31 after its own dry run (243 B to 11.5 KB; joins of two or three tables bill 20 to 40 MB, each table's 10 MB minimum).
- 06:41Z: `net_sales_daily` against dbt's `exposed.net_sales_daily` over the same range.
- 06:43Z to 06:48Z: [`probes/329_shaped_agent.py`](../probes/329_shaped_agent.py) created the data agent `projects/pplk8s-lab-001/locations/us/dataAgents/bet-shaped` through `platform/gcp/data-agent/publish.py`'s publisher (the pinned v1 schema, revision 20261022; staging, then published) and asked it seven probe questions, three times:
  run 1 with the full context (the seven silver tables the functions read, the seven functions in `userFunctions.bqRoutines` with their descriptions, one verified query per saved query, ``SELECT * FROM `bet_shaped.<f>`(@start_date, @end_date)`` with two `DATE` parameters, a system instruction saying to call the functions, the lab's byte cap); run 2 the same without the verified queries (`--no-examples`); run 3 the full context again, which the agent keeps for #333.
  Five questions fit a saved query's shape (four at a coarser grain than the saved query: a month's total, a quarter); two don't (average order value by country, a metric the project defines and no saved query holds; new customers in a month, which no metric defines).
- Every row, with the agent's SQL, its matched verified query, its final text and the right answer read through the functions (or, for the two uncovered questions, the project's definition over silver): [`2026-11-03-329-bet-shaped.jsonl`](2026-11-03-329-bet-shaped.jsonl); the raw streams stayed in the session.
- 06:48Z: the cost and usage checks again (ok, unchanged); `INFORMATION_SCHEMA.JOBS_BY_USER` since 06:43Z: 50 query jobs, 520 MiB billed, the agent's 25 of them 340 MiB (`JOBS_BY_PROJECT` is refused to this credential).

### What was observed (`measured`, the runs above)

- `bqRoutines` takes table functions: the create and the publish accepted all seven, a GET of the published context returns them, and each chat's first step says "Retrieving context for 7 tables and 7 user functions".
- The functions give dbt's numbers on live data: over August to October `net_sales_daily` sums to revenue 19,793.59, 6 returns, net 19,703.84, exactly `exposed.net_sales_daily`'s.
- Parameterised verified queries are matched on meaning and filled in: run 1 matched four of the five covered questions and run 3 four, each with the right dates as parameter values (`2026-09-01`/`2026-09-30` for "September 2026", `2026-07-01`/`2026-09-30` for "the third quarter of 2026"); a match is a fast path (the citation's source id `fast_path_verified_query`) whose stream has `matchedQuery` and `bigQueryJob` and no `generatedSql`.
- The fast path answers at the verified query's grain, not the question's: asked for September's net revenue, both runs that matched returned 30 daily rows and the text "The result shows daily net revenue, revenue, and returns for each day in September 2026", with no total; run 3's matched "revenue by customer country in September" did the same.
  Unmatched, the same question got the right total (run 2: "€12,582.75", by summing the function's rows).
- Without verified queries (run 2) the agent called the matching function for all five covered questions and all five answers were right: the total above, cost per lead (email €10.00, search €46.00, social €46.67), the cancellations of 1 to 7 October (2, 3, then 0, its `COALESCE` of MetricFlow's NULLs), no partner returns in Q3 (true: every return is in October), revenue by country.
- A function invites the wrong ratio: asked for average order value by country, the agent divided the function's `revenue_eur` by its `orders_total` in runs 2 and 3 (Germany €111.06), but `orders_total` counts cancelled orders and the project's `average_order_value_eur` divides by non-cancelled ones (Germany €121.16); in run 1 it wrote its own SQL over silver, excluded cancelled orders, and got €121.16.
  It stated its definition in run 1 and not in runs 2 and 3: a confident wrong number, the failure #333 scores.
- Questions no function covers went to the agent's own SQL over silver, correctly: new customers in September, 0 in all three runs (true: 10 customers first ordered in August, 7 in October).
- Per run, right answers out of seven: run 1 five (one total missing, average order value right), run 2 six (average order value wrong), run 3 four (two totals missing, average order value wrong).
- Each chat took 5 to 17 s; matched questions were the quickest (5 to 7 s).

### What it means for the verdict

- Q4's "does `bqRoutines` take a table function" is answered: yes, and an agent told to prefer the functions does call them, with the right dates, without being forced (no setting forces it).
- Shaping works where the question's shape is the function's: the date-range trap part 1 found (filters in every input of `channel_performance`) never reached the agent, which only passed two dates.
- Two costs show up that a semantic layer's query interface doesn't have: a verified query answers at its own grain (a daily table for a monthly question), and a function's columns get recombined into metrics it doesn't define (average order value from `orders_total`).
  Both are cheap to mitigate in content (verified queries per grain asked; a column named for what it counts, or the ratio in the function), but each needs someone to foresee the question: the shaped arm moves the semantic layer's job into hand-written content.
- For #333: `bet-shaped` holds the full context (run 3's); the average-order-value question is a ready trap for this arm.

### Still unknown (part 2)

- How often each behaviour holds: one run per configuration, so these are shapes, not rates; #333 runs the frozen set with k runs.
- Whether a verified query phrased at the question's grain (a total over the range) is matched instead of the daily one, or whether the fast path can aggregate: not tried.
- Views: the arm has table functions only; a view of a saved query has no date arguments, so the date trap would return.
