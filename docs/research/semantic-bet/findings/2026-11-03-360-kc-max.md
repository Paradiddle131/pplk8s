## Question

What happens when Google's data agent is fed every piece of Knowledge Catalog context the lab project can hold, not only the dbt import ([#327](2026-11-03-327-kc-data-agent.md): the import, a one-line instruction, 7 tables, never named a metric)?

## The design (the probe, [`probes/360_kc_max.py`](../probes/360_kc_max.py))

- **Copies, not `silver` itself**: a data agent imports the terms linked to its tables, so terms linked to `silver`'s columns would reach `bet-kc`, `bet-context` (whose runs 2 and 3 are under way) and the main track's `pplk8s-semantic` too, and descriptions written on `silver` would change what every silver arm reads, then vanish at the next build (`silver` has no `persist_docs`).
  So the arm reads `bet_kcmax`, a `bq cp` of the 16 silver tables the semantic models read (US, free; only the copies' storage counts, a few KiB against BigQuery's free 10 GiB), and only `bet_kcmax` gets descriptions and links.
  It costs the dbt import's `reference` links, which #327 measured as making no difference.
- **(a) Descriptions**: each model's and declared column's `description` from the manifest (the words `persist_docs` writes), `silver.<table>` rewritten to `bet_kcmax.<table>`: 16 `ALTER TABLE ... SET OPTIONS` and 85 `ALTER COLUMN IF EXISTS ... SET OPTIONS`, each dry-run first and refused if the dry run bills a byte, each run with `free-path.yaml`'s cap.
- **(b) The glossary** `bet-kc-max` in `us` (the entries' location): 71 terms, one per metric (57: label, description, and the definition written out from the semantic manifest, such as `revenue_eur / orders_total (where status <> 'cancelled')` for the average order value) and one per business term (14, from `config.meta.glossary`, with synonyms, metrics and dimensions in the text), the same terms the generated context's 71 `glossaryTerms` carry.
  Each term is linked (`definition` entry links, `Schema.<column>`) to the columns it reads: a metric's aggregated column and filter columns, a ratio's or formula's inputs' columns, a business term's dimension columns (else its metrics').
  The 10-terms-a-table cap is applied before any run, from the term's shape only: business terms first, then simple metrics, then formulas, then a metric's time windows (cumulative, or derived with an offset), ties by id; one-table terms take the slots first, then a multi-table term is linked on each of its tables with room.
  Result: 99 links over 14 tables; 67 terms reach at least one table; 4 reach none (`engaged-customers-7d`, `repeat-revenue-share`, `revenue-eur-mtd`, `revenue-eur-wow-growth`, all on full tables) and stay searchable in the glossary; `orders` and `customer_actions` are at 10.
  Two links point at columns the YAML does not declare (`ad_spend.clicks`, `returns.amount`, read from the metrics' `expr`); both columns exist (read below), and the paste prints each link's status.
- **The agent** `bet-kc-max`: native-kc's one-line instruction, no authored glossary, no verified queries, over the 16 copies plus `semantic.time_spine` and the three `legacy` tables (native-context's tables, the silver ones as copies), the lab's byte cap; `354_data_agent.py` knows it as `native-kc-max`.
- Size: the plan's JSON is 35,914 bytes; with the dbt import's 290,315 bytes of entries it is under Knowledge Catalog's free 1 MiB of metadata a month (an estimate from the bodies; the stored size is not readable).

## What it means for the verdict (so far)

- Of the Knowledge Catalog pieces, only two are both stated as read by a data agent and free: BigQuery descriptions and a business glossary linked to columns (capped at 10 terms a table); context sets, the piece built for agent grounding, are not stated for data agents, and data insights, profiles and inferred relationships cost money.
- The glossary is the generated context's glossary moved into the catalog; if the arm scores near `native-context`, the catalog route matches ours without authored context, and if it scores near `native-kc`, the data agent does not take a catalog glossary from an API-created agent.
