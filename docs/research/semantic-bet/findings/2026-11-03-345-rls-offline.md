## What the docs say (`stated`, read 2026-11-03)

- Views: "The data displayed in either type of view is filtered according to the underlying source table's row-level access policies" ([row-level security with other features](https://docs.cloud.google.com/bigquery/docs/using-row-level-security-with-features)).
- Table functions, UDFs, routines and authorized routines: not mentioned on that page, nor on the [row-level security overview](https://docs.cloud.google.com/bigquery/docs/row-level-security-intro), nor on [authorized routines](https://docs.cloud.google.com/bigquery/docs/authorized-routines), which says only that authorization "lets users run the routine without table-level permissions" and that table functions, UDFs and stored procedures can be authorized.
  Unchanged since the 2026-11-02 reading: whether an authorized table function keeps the caller's row filter is still undocumented.
- Conversation logging ([overview](https://docs.cloud.google.com/bigquery/docs/conversation-logging-overview)): "If the check finds a policy or can't confirm that there are none, the turn isn't logged"; "The check doesn't look through views to the tables behind them"; "A view over a table that uses these policies can pass the check, so its turns can be logged."
  Routines and table functions are not mentioned, so a table function as a knowledge source is outside what the check is documented to inspect.
- What a logged turn keeps: not the generated SQL ("but not the queries that produced them"), not the tool calls ("the model's output is removed, including the name and arguments of any tool that it called"), but answers "can still include values returned from knowledge sources"; enabled per agent by `bigqueryAgentAnalyticsEnabled` and `bigqueryAgentAnalyticsTable`; no separate charge, standard BigQuery storage, Storage Write API and query prices (same page).
- Data agents: a user must be granted rows through the policy on any row-policied source, else `Schema_Resolution: Access Denied` ([analyze data with conversations](https://cloud.google.com/bigquery/docs/create-conversations)).

## What the live run must show (#332)

- `probes/332_rls_check.sh` on the lab project: the four counts for the caller the policy names, 3 rows and 60 where the policy holds, 6 and 150 where a path bypasses it; the views' line is documented, so the table function's and the authorized table function's are the new facts.
- It checks `bigquery.rowAccessPolicies.create` with `testIamPermissions` before creating the policy (exit 4 and a needs-user packet if not held), dry-runs every statement and caps every job at 10 MiB.
- The conversation-log half is likely unmeasurable here: `semantic/PLAN.md` § 6 records that outside the BigQuery Agent Analytics preview the API drops `bigqueryAgentAnalyticsEnabled` and the console saved neither field, so no log table appeared (#207, 2026-11-02); #332 should try once with a view as the source and, if no table appears, record "still unknown" rather than infer it.

## What it means for the verdict

- Through views the row filter is a documented guarantee; through table functions and authorized routines, which the shaped arm (#329) and generated Toolbox tools (#330) rely on, it is not, so a governed-tools design that has to hold row security must either measure it (#332) or keep row-scoped sources behind views.
- The logging check's blind spot is documented, not inferred: a view over a row-policied table can switch logging on, and logged answers may hold the row-scoped values, so "generate views over governed tables" carries a privacy cost an owner must accept knowingly.

## Still unknown

- Whether a table function, and an authorized table function, keep the caller's row filter (live, #332).
- Whether the logging check inspects a table function or a routine at all, and what a logged turn holds for a row-scoped answer read through a view (live, and gated on the preview above).
