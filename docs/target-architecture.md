# Target architecture: an agent-ready warehouse on BigQuery

One page a BigQuery team can adopt from the lab: the layers and their datasets, how models are named, where each calculated field lives, what the documentation says, how it is monitored, who reads what, and how consumers move over.
It is a brief: each section is a few lines, the document that holds the rules, and the `make` target that proves them on the lab ([`semantic/PLAN.md`](../semantic/PLAN.md) U1-U6).
Everything runs on synthetic data, on Postgres and on the BigQuery emulator; real BigQuery is the final word on what the emulator measured.
[`demo.md`](demo.md) walks the same story live in ten minutes; this page is what stays after the call.

## Layers and datasets

One folder under `dbt/models/` per layer and one BigQuery dataset per folder: `bronze` (the landing tables cast, one to one), `silver` (one row per natural key; the semantic models sit here), `gold` (business aggregates at a stated grain), `exposed` (gold shaped for one consumer), and `semantic` (the time spine, `metrics`, `glossary`).
`legacy` and `migration` exist only while consumers move; `ops` holds the readiness ledger, the source freshness verdicts and the agent audit.
The landing dataset `ds_source` belongs to the extraction service; dbt reads it only through `source()` in bronze.
A model builds in its layer's dataset, never in one it chooses.

- Rules: [`agent-ready-warehouse.md` § Datasets per layer](agent-ready-warehouse.md#datasets-per-layer)
- Proof: `make dbt-validate` (the standard's check), `make bigquery-emulator-check` (the layers built and tested on GoogleSQL)

## Naming

A model carries its layer's prefix (`brz_`, `slv_`, `gld_`, `exp_`, `lgc_`) and builds a relation named without it: `gld_daily_sales` is `gold.daily_sales`.
Everything is lower snake case; a metric ends in its unit (`revenue_eur`), a count names what it counts, a ratio of counts ends in `_rate`; a dimension is asked for as `<entity>__<dimension>`.

- Rules: [`agent-ready-warehouse.md` § Naming](agent-ready-warehouse.md#naming)
- Proof: `make dbt-validate`; `make semantic-check` shows it failing on an unprefixed gold model

## Where each calculated field lives

Every calculated field is one metric in the semantic YAML, over silver: a sum, count or distinct count in its silver model's YAML, a ratio, derived or conversion metric, built from other metrics, in `dbt/models/semantic/semantic.yml`.
Gold and exposed keep their hand-written aggregates only as the parity oracle; a new number an agent should answer becomes a metric first.
A routine or scheduled query that computes a business number moves into a metric, never into a UDF ([`routines-and-scheduled-queries.md`](routines-and-scheduled-queries.md)).
The table holds the rows of `semantic.metrics`, and a metric defined for one warehouse only (`median_order_value_eur`, BigQuery); `dbt/scripts/check_brief.py` (in `make dbt-validate`) fails when a metric is missing from it or a row differs from the project.

## The documentation standard

A description is written for a reader who sees only it: a model says its grain and time zone, a column its unit and what is in or out, a code column its codes (declared as `accepted_values`, so the agent's filter refuses a guessed value), a metric its label and what a ratio divides.
A business term that is not a metric is a glossary term on the model that holds the concept, mapped to its metrics and dimensions.
Gold and exposed are public with enforced contracts, so a renamed or retyped column fails the build before it replaces the table.
The words reach BigQuery's descriptions through `persist_docs`, and the data agent's authored context and verified queries through `build_catalog.py`.

- Rules: [`agent-ready-warehouse.md` § What every description says](agent-ready-warehouse.md#what-every-description-says), [§ The glossary](agent-ready-warehouse.md#the-glossary)
- Proof: `make dbt-validate` (`check_standard.py`), `make catalog-check` (every gold and exposed column commented in the warehouse), `make bigquery-check` (the catalog and verified queries in BigQuery's dialect, offline)

## Monitoring

Three checks, each where its failure is cheapest:
- **A source that stops flowing:** `dbt source freshness` against thresholds declared once in `sources.yml`, its verdict written to `ops.source_freshness`, an alert on it (SL-12); on GCP a scheduled Cloud Run Job and a Cloud Monitoring alert.
- **A hop that loses or doubles rows:** `hop_<from>_to_<to>` tests in `dbt build`, from bronze to the metrics, so a mismatch fails the build that would publish it (SL-9).
- **A product that is late:** the readiness ledger (`ops.readiness`, `ops.product_deadlines`) states each pipeline layer's newest ready interval, and every agent answer quotes the freshness of its metrics (SL-4).

- Rules: [`semantic-layer-on-bigquery.md` § The mapping](semantic-layer-on-bigquery.md#the-mapping) (the freshness Job and alert)
- Proof: `make source-freshness-check`, `make rules-test`, `make semantic-check` (the hops), `make agent-standalone-check` ("Freshness unknown" with no ledger)

## Access and audit

Agents read gold, exposed and metrics only, marked `access: public` in dbt; an agent reaches silver only through a metric's definition.
Each deployed agent gets its own service account with dataset-level read on the datasets it may see: the semantic agent on `silver` and `semantic`, plus the two `ops` tables its freshness reads (option A of the proposal).
Every data query leaves a row in the agent's own record; on BigQuery the Data Access audit log, which cannot be turned off, is the record of what was read, and job labels join it to the conversation.

- Rules: [`semantic-layer-on-bigquery.md` § Agent access and audit](semantic-layer-on-bigquery.md#agent-access-and-audit), [`agent-ready-warehouse.md` § Which layer agents read](agent-ready-warehouse.md#which-layer-agents-read)
- Proof: `make agent-warehouse` (roles, grants and the audit table from the dbt project), `make agent-standalone-check` (one turn, one audit row), `make agent-test`

## Migration

Build the new layers beside the old tables, list each consumer as a dbt exposure, compare each old table with its new model per field in `migration.parity`, and switch consumers one at a time: dashboards, then agents, then automations.
A test fails the build that would switch a consumer with an unaccepted difference or out of order; rolling back is pointing it at the old table again.
Scheduled queries become dbt models, stored procedures stay only for work dbt cannot express, and a routine moves one at a time beside its replacement.

- Rules: [`migration-rehearsal.md`](migration-rehearsal.md), [`routines-and-scheduled-queries.md`](routines-and-scheduled-queries.md)
- Proof: `make migration-check`, `make bigquery-emulator-check` (the same 13 parity rows on the emulator)

## Not proven here

- Anything on real BigQuery: the compiled SQL, the descriptions `persist_docs` writes, the job labels, the audit log entries; the emulator and the documentation stand in ([`semantic-layer-on-bigquery.md` § Unverified](semantic-layer-on-bigquery.md#unverified)).
- A native data agent's answers: the context is generated and checked, not yet scored against one.
- IAM: the access model is a proposal; the lab enforces it with warehouse roles.
